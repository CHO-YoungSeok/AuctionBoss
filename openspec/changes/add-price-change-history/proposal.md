# Proposal: add-price-change-history

## Why

10분마다 수집하는 이유는 물건이 **변하기** 때문이다. 유찰되면 최저매각가격이 감정가의 80% → 64% → 51%로 떨어지고 유찰횟수가 오르며 매각기일이 새로 잡힌다. 그런데 현재는 `upsertItems`가 기존 행을 덮어쓰기만 해서 **변화의 기록이 남지 않는다.** 10분 주기 수집의 산출물이 "지금 상태" 하나뿐이라면 하루에 한 번 수집하는 것과 다를 게 없다.

또한 분석은 물건당 1회만 실행되고 재분석 경로가 없다. 최저가가 30% 떨어진 뒤에도 처음 가격을 기준으로 쓴 분석이 그대로 남아 있으면 오히려 틀린 정보가 된다. 프롬프트를 개선해도(원래 목표) 기존 물건에 반영할 방법이 없다.

## What Changes

- 수집 시 물건의 감시 대상 필드(최저매각가격, 유찰횟수, 매각기일, 진행상태)가 이전 값과 달라지면 변경 이력을 기록한다. 값이 그대로인 회차는 이력을 남기지 않는다(10분마다 같은 행이 쌓이면 안 된다).
- 최초 수집 시점의 값도 이력의 첫 항목으로 기록해, 이후 변화를 기준점과 비교할 수 있게 한다.
- 물건 상세 페이지에 변경 이력을 시간순으로 표시한다(무엇이 언제 어떻게 바뀌었는지).
- 목록에 "최근 변동" 신호를 노출한다 — 최근에 최저가가 떨어진 물건을 알아볼 수 있어야 한다.
- 변경 이력 조회 API를 제공한다.
- **재분석**: 감시 대상 필드가 변경된 물건은 다시 분석 대상이 된다. 또한 분석 워커의 프롬프트 버전이 저장된 분석의 버전보다 새로우면 재분석 대상이 된다.
- 재분석 시 이전 분석을 지우지 않고 새 행으로 쌓는다(이미 `analyses`가 물건당 다중 행을 허용하도록 설계돼 있다). 상세 화면은 최신 것을 보여주되 이전 분석도 볼 수 있게 한다.
- 재분석 폭주 방지: 한 회차에 재분석할 최대 건수를 설정으로 제한하고, 신규 물건 분석과 재분석의 우선순위를 정한다.

비목표(후속): 가격 변동 차트/그래프 시각화, 변동 알림(푸시·메일), 이력 기반 낙찰가 예측, 분석 결과 간 diff 표시.

## Capabilities

### New Capabilities

- `auction-history`: 물건의 변경 이력 기록·조회 — 감시 대상 필드, 변경 감지 규칙, 이력 저장, 이력 조회 API, 상세·목록에서의 표시.

### Modified Capabilities

- `auction-collection`: "저장 및 중복 처리" 요구사항에 변경 감지와 이력 기록이 추가된다(upsert가 변경을 감지해야 한다).
- `auction-analysis`: "분석 대상 선정" 요구사항이 미분석 물건뿐 아니라 변경된 물건과 프롬프트 버전이 낡은 물건까지 포함하도록 확장된다. "분석 결과 표시" 요구사항에 이전 분석 열람이 추가된다.

## Impact

- 새 테이블(변경 이력) + 스키마 마이그레이션(기존 DB 파일에 적용돼야 한다).
- `upsertItems`가 변경 감지 로직을 갖게 되며, 반환값에 변경 건수가 추가된다.
- 분석 대상 선정 쿼리가 "미분석" 단일 조건에서 "미분석 OR 변경됨 OR 프롬프트 낡음"으로 확장된다 — `GET /api/items?analyzed=false`의 의미를 바꾸지 않고 별도 파라미터로 노출해야 기존 계약이 유지된다.
- `workers/analyzer.ts`의 대상 조회 방식과 회차당 건수 배분 변경.
- `config/collector.json`에 재분석 관련 설정 추가.
- 분석 비용: 재분석이 생기면 Claude 호출 수가 늘어난다. 상한 설정이 필수다.
