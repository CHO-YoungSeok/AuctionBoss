# Design: add-price-change-history

## Context

동기는 proposal.md 참조. 현 구조에서 관련된 사실:

- `upsertItems(items, {now})`가 트랜잭션 안에서 자연 키로 존재 여부를 먼저 `SELECT`한 뒤 `ON CONFLICT DO UPDATE`를 실행하고 `{inserted, updated}`를 반환한다. **이미 이전 행을 조회하는 지점이 있어** 변경 감지를 끼워 넣기에 자연스럽다.
- `analyses` 테이블은 처음부터 물건당 다중 행을 허용하도록 설계됐고(`prompt_version` 컬럼 포함), `getLatestAnalysis`가 최신 1건을 반환한다. 재분석에 스키마 변경이 필요 없다.
- 분석 워커는 `GET /api/items?analyzed=false&pageSize=N`만 호출하며, `analyzed` 필터의 의미는 스펙의 "기존 계약 유지" 시나리오로 고정돼 있다.
- 프롬프트 버전은 `workers/lib/prompt.ts`의 `PROMPT_VERSION` 상수이고, 템플릿 파일의 주석과 일치하는지 테스트로 고정돼 있다.

## Goals / Non-Goals

**Goals:**
- 값이 변할 때만 이력이 쌓이고, 변하지 않으면 10분마다 아무것도 쌓이지 않음
- 물건 갱신과 이력 기록의 원자성
- 재분석 대상 선정이 기존 `analyzed` 필터 의미를 바꾸지 않음
- 재분석 비용 상한

**Non-Goals:**
- 변동 차트/그래프, 알림, 낙찰가 예측, 분석 간 diff

## Decisions

### D1. 이력 저장 형태: 필드 단위 행(long format)

`item_changes(id, item_id, field, old_value, new_value, changed_at)` — 한 회차에 두 필드가 바뀌면 2행이 생긴다.

- 왜 스냅샷(행 전체 복제)이 아닌가: 스냅샷은 "무엇이 바뀌었는지"를 조회 시점에 매번 이전 행과 비교해 계산해야 한다. 화면이 실제로 원하는 것은 "언제 무엇이 얼마에서 얼마로"이므로 그 형태로 저장하는 게 직접적이다. 또 감시 필드가 4개뿐이라 long format의 행 증가가 감당 가능하다.
- 왜 필드별 컬럼(`old_min_bid_price`, `new_min_bid_price`, …)이 아닌가: 감시 필드를 추가할 때마다 스키마가 바뀐다. long format은 `field` 값만 늘어난다.
- `old_value`/`new_value`는 TEXT로 저장한다. 가격은 정수, 매각기일은 날짜 문자열, 상태는 문자열이라 타입이 섞인다. 표시 시 `field`에 따라 해석한다. 숫자 비교가 필요한 쿼리는 현재 요구사항에 없다(변화폭 계산은 표시 계층에서 한다).
- `field`는 도메인 필드명(`minBidPrice`, `failedBidCount`, `auctionDate`, `status`)을 쓴다 — DB 컬럼명(snake_case)이 아니라. 이력은 화면과 API로 직접 노출되고, snake_case를 `src/lib/db` 밖으로 내보내지 않는다는 기존 규칙을 따른다.
- 인덱스: `(item_id, changed_at DESC)`.

### D2. 최초 저장의 기준점 행

물건이 처음 저장될 때 감시 필드 4개에 대해 `old_value = NULL, new_value = <값>`인 행을 만든다.

- 왜 필요한가: 기준점이 없으면 "최초 8억이었는데 지금 5억"을 이력만 보고 알 수 없다. 첫 변경 이력의 `old_value`가 그 역할을 하지만, 아직 한 번도 안 바뀐 물건은 이력이 통째로 비어 최초 값조차 없다.
- 값이 NULL인 감시 필드는 기준점 행을 만들지 않는다 — `old_value`도 `new_value`도 NULL인 무의미한 행이 된다.
- 스펙의 "변동이 없는 물건 상세" 시나리오는 이력이 기준점뿐인 상태를 뜻한다. 따라서 표시 계층은 **기준점과 실제 변경을 구별할 수 있어야** 한다: `old_value IS NULL`이 기준점이다.

### D3. 변경 감지는 `upsertItems` 안에서, 같은 트랜잭션으로

기존 upsert가 이미 하는 사전 `SELECT`를 확장해 감시 필드까지 읽고, 새 값과 비교해 다른 필드만 이력 행을 추가한다. 전체가 하나의 `db.transaction`이므로 스펙의 원자성 요구가 자동으로 만족된다.

- 비교 규칙: `null`과 `null`은 같음, `null`과 값은 변경. 가격·유찰횟수는 숫자로 비교하고(문자 `"100"`과 숫자 `100`을 다른 값으로 오판하지 않도록 도메인 타입이 이미 숫자다), 날짜·상태는 문자열로 비교한다.
- 반환값을 `{inserted, updated, changed}`로 확장한다. `changed`는 **감시 필드가 실제로 바뀐 물건 수**(이력 행 수가 아니라 물건 수)다 — 스펙 시나리오가 "변경 감지 1건"으로 물건 단위를 요구한다. 기준점 행은 `changed`에 세지 않는다(신규는 `inserted`가 이미 센다).
- 왜 별도 함수로 분리하지 않는가: 감지에는 "이전 값"이 필요하고 그건 upsert가 덮어쓰기 전에만 존재한다. 밖으로 빼면 같은 `SELECT`를 두 번 하거나 트랜잭션을 쪼개야 한다.

### D4. 재분석 대상 선정: `analyzed` 필터를 건드리지 않고 별도 파라미터

`GET /api/items`에 `needsAnalysis=true`를 추가한다. 기존 `analyzed=false`는 그대로 "분석 행이 없는 물건"을 뜻한다.

- 왜 `analyzed=false`의 의미를 확장하지 않는가: 스펙에 "기존 계약 유지" 시나리오가 명시돼 있고, 그 필터는 목록 UI에서도 "분석 여부"로 쓰인다. 의미를 바꾸면 UI 표시가 틀어진다.
- `needsAnalysis` 판정 SQL은 세 조건의 OR다: 분석 행 없음 / 최신 분석의 `analyzed_at` 이후에 실제 변경(`old_value IS NOT NULL`) 이력이 있음 / 최신 분석의 `prompt_version`이 요청된 현재 버전과 다름.
- **프롬프트 버전 비교는 같음/다름으로만 한다.** 세만틱 버전 비교(`v2 > v1`)를 하지 않는 이유: 버전 문자열 형식이 `v1` 같은 자유 문자열이고, 프롬프트를 되돌렸을 때(v2→v1) "낡음"의 방향을 판단할 근거가 없다. 워커가 자신의 현재 버전을 파라미터로 보내고 서버는 불일치만 본다. 스펙 문구는 "낡은 버전"이지만 실제 판정은 "다른 버전"이며, 되돌림도 재분석 대상이 되는 것이 안전한 쪽이다. **이 해석 차이는 의도적이며 여기 기록한다.**
- 재분석 우선순위: 워커가 두 번 조회한다 — 먼저 `analyzed=false`로 신규 한도(`maxItemsPerRun`)만큼, 그 다음 `needsAnalysis=true`로 **재분석 한도(`maxReanalysisPerRun`)만큼**(1차에서 이미 뽑힌 물건은 제외). 두 한도는 **독립**이며 회차 총 호출 수는 두 값의 합이다(D5) — "남은 한도를 나눠 쓴다"가 아니다. 한 쿼리로 정렬해 섞지 않는 이유는 "신규가 재분석에 밀려 무한 연기되지 않아야 한다"는 스펙 요구를 코드로 명백하게 만들기 위함이다. 한도가 독립이므로 재분석 대상이 아무리 많아도 신규 분석 몫이 잠식되지 않는다.

### D5. 설정과 비용 상한

`config/collector.json`의 `analysis`에 `maxReanalysisPerRun`을 추가한다(기본 2, 기존 `maxItemsPerRun`은 신규 분석 한도로 의미를 유지). 총 호출 수 상한은 두 값의 합이다.

- 왜 기본값을 작게: 재분석은 유찰이 발생할 때마다 생긴다. 서울중앙 한 곳에서도 물건이 수백 건이라, 상한이 없으면 유찰이 몰린 날 Claude 호출이 폭증한다.
- 재분석 선정 순서는 **가장 오래 전에 분석된 것 우선**(`analyzed_at ASC`)으로 한다. 최신 변경 우선으로 하면 자주 바뀌는 물건이 한도를 독점한다.

### D6. 목록의 "최근 변동" 신호

목록 행에 최근 변경 여부를 표시한다. 판정은 "실제 변경 이력 중 가장 최근 것이 N일 이내"이고 N은 상수(기본 7일)로 둔다.

- 이력 테이블과의 조인이 목록 쿼리에 추가된다. 필터·정렬이 이미 복잡해진 쿼리라, **최근 변경 시각을 스칼라 서브쿼리로 한 컬럼 추가**하는 방식을 쓴다(`WHERE`/`ORDER BY`에 관여하지 않음). 이렇게 하면 기존 필터·정렬 로직과 `total` 계산을 건드리지 않는다.
- 이번 범위에서 "최근 변동으로 필터/정렬"은 하지 않는다 — 표시만 한다. 필터 추가는 쿼리 조립을 다시 흔들므로 별도 change로 미룬다.

## Risks / Trade-offs

- [이력 테이블이 무한히 커짐] → 실제 변경만 기록하므로 물건당 유찰 횟수 수준(수 건)에 머문다. 값이 안 바뀌면 아무것도 안 쌓인다는 것이 이 설계의 핵심이며 스펙 시나리오로 고정했다. 그래도 수집 범위가 전국으로 늘면 보관 기간 정책이 필요하다.
- [소스 데이터의 노이즈가 가짜 변경으로 기록됨] → 이미 관측된 문제가 있다: `yuchalCnt`와 `minBidPrice`가 어긋나는 행이 존재하고(이전 change의 Open Question), 소스가 같은 물건을 다르게 표기할 수 있다. 가짜 변경은 재분석을 유발해 비용이 된다. 1차 대응은 재분석 상한이고, 이력에 남은 변경 패턴을 실제로 관측한 뒤 필터링 규칙을 정한다.
- [재분석 비용] → D5의 상한. 그래도 프롬프트 버전을 올리면 전체 물건이 재분석 대상이 되므로, 버전 변경은 의도적인 비용 결정이라는 점을 README에 적는다.
- [기존 DB 마이그레이션] → 새 테이블은 `CREATE TABLE IF NOT EXISTS`로 추가된다. **이미 저장된 물건들은 기준점 이력이 없다** — 최초 저장 시점을 소급할 수 없기 때문이다. 이 물건들은 첫 변경이 생길 때까지 이력이 비어 있고, 화면은 그 상태를 "변동 없음"으로 정상 처리해야 한다(빈 이력과 기준점만 있는 이력을 같게 다루면 된다).

## Open Questions

- 가짜 변경 필터링 규칙 — 실제 이력 데이터를 며칠 관측한 뒤에 정해야 한다. 지금 정하면 근거 없는 추측이 된다.
- "최근 변동" 기준 7일이 적절한지 — 매각기일 주기(보통 1개월 이상)를 감안하면 더 길어야 할 수 있다. 상수라 바꾸기 쉽다.
