## 1. 실제 전체 수집

- [ ] 1.1 수집 전 상태를 기록: 현재 DB 물건 수, 최근 회차 기록, `/status` 상태. 비교 기준점이 없으면 무엇이 달라졌는지 알 수 없다
- [ ] 1.2 **한 회차만** 전체 수집 실행(페이지 상한 해제, 기존 `pageDelayMs` 유지). 실행 중 로그를 남기고 끝나면 즉시 중단할 것 — 상주 실행 금지
- [ ] 1.3 실측 기록: 실제 요청 페이지 수, 총 소요 시간, 수신 행 수, 접힌 물건 수, `{inserted, updated, changed}`. 회차 기록(`worker_runs`)에서 읽어 제시할 것
- [ ] 1.4 차단이 발생하면 **그것도 결과다.** 발생 조건(요청 수, 간격, 시각)을 기록하고 즉시 중단. 재시도 루프 금지. 이 경우 이후 태스크는 기존 데이터로 진행
- [ ] 1.5 수백 건 규모에서 목록·상세·필터·정렬이 정상 동작하고 체감 지연이 없는지 확인. 느리면 어느 쿼리인지 특정할 것

## 2. 실제 분석 실행

- [ ] 2.1 분석 워커를 `--once`로 여러 번 실행해 **최소 20건**의 실제 보고서를 누적. 상주 실행으로 방치하지 말 것 — 비용이 관측 없이 쌓인다
- [ ] 2.2 회차당 한도(신규 5 + 재분석 2)와 쿨다운이 의도대로 동작하는지 회차 기록으로 확인
- [ ] 2.3 사용한 Claude 호출 수와 대략의 소요 시간을 기록
- [ ] 2.4 개별 분석 실패가 있었다면 원인별로 분류해 기록

## 3. 보고서 품질 관측 (이번 사이클의 핵심)

- [ ] 3.1 생성된 보고서를 **전부 실제로 읽는다.** 통계만 보면 "성공했지만 쓸모없는 보고서"를 놓친다
- [ ] 3.2 문제를 유형별로 기록: 사실 오류 / 데이터가 있는데 없다고 함 / 헛도는 문장 / 형식 문제 / 길이 문제. **실제 인용과 물건 식별자를 함께 남길 것** — "품질이 낮다"가 아니라 "이 물건에서 이렇게 썼다"로
- [ ] 3.3 반대로 **잘 작동한 사례도 기록**한다. 무엇을 유지해야 하는지 알아야 다음 개선이 후퇴하지 않는다
- [ ] 3.4 **프롬프트를 고치지 말 것.** 품질 개선은 별도 이슈이고, 여기서 손대면 관측 결과가 어느 버전의 것인지 흐려진다(design D2/D5)

## 4. 보고서 표시 형식

- [ ] 4.1 실제 보고서에서 쓰이는 마크다운 구문을 조사(굵게·목록·제목·표 중 무엇이 실제로 나오는지). 추측하지 말고 생성된 본문에서 셀 것
- [ ] 4.2 조사 결과로 판단: 구문이 적으면 라이브러리 없이 처리, 많으면 라이브러리 도입. **판단 근거를 명시할 것**
- [ ] 4.3 라이브러리를 도입한다면 **XSS를 반드시 다룰 것.** 분석 본문은 LLM 출력이라 통제 대상이 아니다. `dangerouslySetInnerHTML` 경로가 생기면 sanitize가 필수다. 현재 `<pre>`는 이 위험이 없다는 것이 장점이므로, 바꿀 때 무엇을 잃는지 알고 바꿀 것
- [ ] 4.4 분석이 여러 건 쌓인 물건에서 최신 보고서를 찾기 쉬운지 실제로 확인

## 5. 운영 관측 확인
