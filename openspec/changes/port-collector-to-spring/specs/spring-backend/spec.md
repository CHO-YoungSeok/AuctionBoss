## ADDED Requirements

### Requirement: 수집·사진 워커 실행
백엔드는 물건 수집 워커와 사진 워커를 자체 실행 단위로 제공해야 한다(SHALL). 두 워커는 `auction-collection`, `item-photos`, `run-observability`, `auction-history`의 기존 요구사항(주기 실행과 겹친 주기 건너뜀, 로테이션과 회차당 법원 수·요청 수 상한, 차단 감지와 공유 백오프, 회차 기록과 결과 구분, 변경 이력과 기준점, 사진 대기열과 재시도 간격, 물건 사이 요청 간격)을 기존 수집기와 같은 동작으로 만족해야 한다(SHALL).

수집 범위, 회차당 상한, 주기, 사진 설정은 기존 수집기와 같은 설정 원천(`config/collector.json`)에서 읽어야 한다(SHALL). 두 수집 구현이 서로 다른 설정을 갖게 되어서는 안 된다(MUST NOT).

외부 소스에 보내는 요청은 기존 수집기와 같은 형식이어야 한다(SHALL): 같은 순서(세션 초기화 → 검색 또는 상세), 같은 요청 본문과 헤더, 같은 고정 브라우저 User-Agent, 같은 페이지·법원·물건 사이 대기 시간. 한 워커 안에서 요청을 동시에 보내서는 안 된다(MUST NOT).

차단 백오프 종료 시각은 기존 수집기와 같은 키와 같은 표기(밀리초 3자리 UTC ISO)로 저장해야 하며(SHALL), 기존 수집기가 쓴 값을 그대로 읽을 수 있어야 한다(SHALL). 로테이션 위치도 기존과 같은 키에 법원 코드로 저장해야 한다(SHALL) — 데이터 이전 뒤 두 값이 그대로 이어져야 하기 때문이다.

사진 파일은 백엔드가 사진 파일 API로 내주는 사진 디렉터리 안에 기존 수집기와 같은 상대 경로 규칙(물건 id 디렉터리, 순번과 실제 이미지 형식에 따른 확장자)으로 저장해야 한다(SHALL).

#### Scenario: 수집 회차 하나
- **WHEN** 수집 워커가 켜진 개발 환경에서 가짜 소스 서버를 상대로 회차 하나를 실행한다
- **THEN** 로테이션이 고른 법원만 요청하고, 물건과 변경 이력이 저장되며, 수집 회차 기록이 성공과 수집 수치(대상 법원, 요청 페이지 수, 가져온 물건 수, 신규·갱신·변경 건수)로 남는다

#### Scenario: 기존 수집기가 남긴 백오프 읽기
- **WHEN** 기존 수집기가 기록한 형식의 백오프 종료 시각(1시간 뒤)이 저장된 상태에서 수집 주기가 도래한다
- **THEN** 외부 요청 없이 사유가 백오프인 건너뜀 회차가 기록된다

#### Scenario: 사진 회차와 파일 저장
- **WHEN** 사진 워커가 가짜 소스 서버에서 사진 2장이 있는 물건 하나를 처리한다
- **THEN** 사진 파일 2개가 사진 디렉터리의 그 물건 디렉터리에 저장되고, 사진 파일 API로 같은 바이트를 내려받을 수 있으며, 사진 회차가 성공으로 기록된다

#### Scenario: 요청 사이 대기
- **WHEN** 한 법원의 결과가 3페이지인 회차를 실행한다
- **THEN** 검색 요청 3개가 순서대로, 겹치지 않고, 요청 사이에 설정된 페이지 대기 시간을 두고 나간다

### Requirement: 수집 스케줄러 기본 꺼짐과 외부 요청 차단
수집 워커와 사진 워커의 주기 실행은 기본으로 꺼져 있어야 한다(SHALL). 각 워커를 켜는 설정을 명시하지 않은 백엔드는 주기 실행을 등록해서는 안 되며(MUST NOT), 기동 로그에 꺼져 있음을 남겨야 한다(SHALL).

외부 소스로 나가는 요청은 외부 요청 허용 설정을 명시하지 않으면 보내서는 안 된다(MUST NOT). 허용되지 않은 상태에서 루프백이 아닌 주소로 요청하려 하면 네트워크에 나가지 않고 요청 실패로 끝나야 한다(SHALL) — 주기 실행 설정이 실수로 켜져도 외부 사이트를 부르지 않게 하는 두 번째 잠금이다.

자동 테스트와 CI는 외부 사이트에 요청해서는 안 된다(MUST NOT). 소스 요청을 다루는 테스트는 루프백의 가짜 서버만 상대해야 한다(SHALL). 개발용 컨테이너 구성과 운영 배포 구성은 이 단계에서 두 설정을 켜서는 안 된다(MUST NOT).

#### Scenario: 기본 설정으로 기동
- **WHEN** 수집 관련 설정 없이 백엔드를 기동하고 수집 주기보다 오래 기다린다
- **THEN** 수집·사진 회차가 하나도 실행되지 않고, 외부로 나간 요청이 없으며, 기동 로그에 두 워커가 꺼져 있다고 남는다

#### Scenario: 외부 요청 허용 없이 실제 주소
- **WHEN** 외부 요청 허용 설정 없이 소스 주소를 루프백이 아닌 주소로 두고 회차를 실행한다
- **THEN** 네트워크 요청이 나가지 않고 그 회차가 요청 실패로 기록되며, 차단 백오프는 걸리지 않는다

#### Scenario: 배포 구성
- **WHEN** 개발용 컨테이너 구성과 운영 배포 구성의 백엔드 설정을 확인한다
- **THEN** 수집·사진 주기 실행과 외부 요청 허용 설정이 켜져 있지 않다

### Requirement: 회차 단일 실행
수집 회차와 사진 회차는 각각 동시에 하나만 실행되어야 한다(MUST). 같은 데이터베이스를 쓰는 백엔드 인스턴스가 여럿이어도 이 조건이 지켜져야 한다(MUST) — 프로세스 메모리의 실행 표시만으로 판단해서는 안 된다(MUST NOT).

실행 중인 회차가 있어 이번 주기에 회차를 시작하지 못하면, 기다렸다가 이어서 실행해서는 안 되며(MUST NOT) 사유가 `overlap`인 건너뜀 회차를 기록해야 한다(SHALL). 회차가 끝나거나 실패하거나 실행하던 인스턴스가 죽으면 단일 실행 표시는 사람의 개입 없이 풀려야 한다(SHALL) — 남은 표시 때문에 수집이 영구히 멈춰서는 안 된다.

수집 회차와 사진 회차는 서로를 막지 않는다(SHALL). 두 워커의 요청 예산 공유는 공유 백오프와 각 워커의 요청 간격으로 다룬다(기존 요구사항).

#### Scenario: 두 인스턴스의 같은 주기
- **WHEN** 같은 데이터베이스를 쓰는 백엔드 인스턴스 둘이 같은 시각에 수집 회차를 시작하려 한다
- **THEN** 한 인스턴스만 소스에 요청하고, 다른 인스턴스는 사유가 `overlap`인 건너뜀 회차를 기록한다

#### Scenario: 회차가 주기보다 오래 걸림
- **WHEN** 회차 하나가 주기보다 오래 걸린다
- **THEN** 그 사이에 도래한 주기는 건너뜀으로 기록되고, 회차가 끝난 직후 밀린 회차가 몰아서 실행되지 않는다

#### Scenario: 실행 중 인스턴스 종료
- **WHEN** 회차를 실행하던 인스턴스가 강제로 종료된 뒤 다른 인스턴스의 주기가 도래한다
- **THEN** 다른 인스턴스가 회차를 정상으로 시작한다

#### Scenario: 실패한 회차 뒤
- **WHEN** 회차가 응답 형식 오류로 실패한 뒤 다음 주기가 도래한다
- **THEN** 다음 회차가 정상으로 시작한다

### Requirement: 수집 저장과 회차 기록의 트랜잭션 경계
한 수집 회차가 저장하는 물건과 그 물건들의 변경 이력은 한 트랜잭션으로 함께 반영되거나 함께 취소되어야 한다(MUST). 회차 기록(시작, 종료, 건너뜀), 로테이션 위치, 백오프 종료 시각은 물건 저장과 다른 트랜잭션이어야 한다(SHALL) — 물건 저장이 취소된 회차도 실패 기록과 로테이션 위치는 남아야 하고, 회차 기록 저장 실패가 물건 저장을 취소해서는 안 된다(MUST NOT).

백오프 종료 시각 기록은 읽기·비교·쓰기가 하나의 원자적 동작이어야 한다(SHALL). 두 워커가 동시에 기록해도 더 늦은 종료 시각이 남아야 한다(MUST).

#### Scenario: 이력 기록 실패
- **WHEN** 수집 회차의 변경 이력 저장 중 오류가 난다
- **THEN** 그 회차의 물건 변경이 하나도 반영되지 않고, 회차는 실패로 기록되며, 로테이션 위치는 기존 수집기와 같게 이번 회차 대상 다음 법원으로 저장된다

#### Scenario: 회차 기록 실패
- **WHEN** 회차 종료 기록 저장이 실패한다
- **THEN** 물건과 변경 이력은 정상으로 저장되어 있고 기록 실패는 로그로 남는다

#### Scenario: 백오프 동시 기록
- **WHEN** 두 워커가 거의 같은 시각에 각각 1시간 뒤와 2시간 뒤 종료 시각을 기록한다
- **THEN** 저장된 종료 시각은 2시간 뒤다

### Requirement: 소스 형식 격리의 기계적 강제
백엔드에서 외부 소스에 접근하는 코드는 소스 어댑터 안에만 있어야 하며(MUST), 이 경계는 빌드 검사(자동 테스트)로 강제되어야 한다(SHALL). 검사는 최소한 다음을 확인해야 한다(SHALL).

- 소스 어댑터 밖의 코드(수집·사진 워커, 저장, API)는 어댑터 구현이 아니라 소스 중립 계약에만 의존한다.
- 소스 어댑터는 데이터베이스 접근 코드에 의존하지 않는다.
- 외부 HTTP 요청 코드는 소스 어댑터 안에만 있다.
- 소스 고유 필드명(예: 검색 결과·차단 표시·사진 목록 필드명)이 어댑터 밖 코드에 나타나지 않는다.

#### Scenario: 경계 위반
- **WHEN** 수집 워커 코드가 소스 어댑터 구현이나 소스 고유 응답 형식을 직접 참조하도록 바꾼다
- **THEN** 백엔드 빌드 검사가 실패한다

#### Scenario: 어댑터의 데이터베이스 접근
- **WHEN** 소스 어댑터가 데이터베이스 저장소를 참조하도록 바꾼다
- **THEN** 백엔드 빌드 검사가 실패한다

### Requirement: 소스 어댑터 동등성
백엔드의 소스 어댑터는 기존 수집기의 어댑터와 같은 응답에 대해 같은 결과를 내야 하며(SHALL), 이를 기존 어댑터로 만든 골든과 기계적으로 비교해 증명해야 한다(SHALL). 비교 입력은 기존 어댑터 테스트가 쓰는 응답 샘플(실제 응답 샘플, 차단 응답 샘플, 형식 위반 샘플)이다.

비교 대상은 다음이다(SHALL).
- 정규화된 물건 목록(필드 값, 없음과 0의 구별, 원문 보존 코드, 필수 키 누락 행 제외, 일괄매각 행 접기)과 실제 요청 페이지 수
- 사진 조회 결과(순번, 이미지 데이터, 요청 수)
- 실패 분류(WAF 차단, 로봇탐지 차단, 응답 형식 오류, 요청 실패)와 실패 시점까지의 실제 요청 수
- 실제로 보낸 요청의 순서, 메서드, 경로, 본문, 헤더와 요청 사이 대기 시간

#### Scenario: 정상 응답 골든 일치
- **WHEN** 기존 어댑터 골든의 응답 시퀀스를 가짜 서버로 재생해 백엔드 어댑터로 조회한다
- **THEN** 정규화된 물건, 요청 페이지 수, 보낸 요청과 대기 시간이 골든과 같다

#### Scenario: 차단 3단 감지 일치
- **WHEN** WAF HTML 페이지, `ipcheck`가 거짓인 응답, 데이터 객체가 없는 응답을 각각 재생한다
- **THEN** 각각 WAF 차단, 로봇탐지 차단, 응답 형식 오류로 골든과 같게 분류되고, 데이터 객체가 없는 응답은 차단으로 분류되지 않는다

#### Scenario: 두 번째 페이지에서 차단
- **WHEN** 첫 페이지는 정상이고 두 번째 페이지에서 차단 응답을 재생한다
- **THEN** 차단으로 분류되고 실패 시점까지의 요청 페이지 수가 골든과 같은 2다

### Requirement: 수집 저장 결과 동등성
같은 소스 응답 시퀀스와 같은 고정 시각이 주어지면 백엔드의 수집·사진 워커는 기존 수집기와 같은 저장 결과를 만들어야 하며(SHALL), 이를 기존 워커로 만든 골든과 기계적으로 비교해 증명해야 한다(SHALL). 비교 대상은 물건, 변경 이력(기준점과 변경의 구별 포함), 회차 기록(결과 구분, 오류 종류, 수치, 변경 건수), 로테이션 위치와 백오프 종료 시각, 사진 기록과 사진 파일 내용이다.

시퀀스는 최소한 신규 저장과 기준점, 감시 필드 변경, 감시 대상이 아닌 필드만 바뀐 갱신, 값이 없던 필드에 값이 생김, 한 회차 안의 같은 물건 중복, 요청 수 상한으로 다음 법원 미시작, 로테이션 이어가기와 설정에서 법원 삭제, 차단과 백오프 건너뜀, 응답 형식 오류, 사진 저장·사진 없음·일부 실패·전부 실패·차단·재시도 간격을 포함해야 한다(SHALL).

#### Scenario: 저장 골든 일치
- **WHEN** 기존 워커로 만든 저장 골든의 응답 시퀀스를 같은 고정 시각으로 백엔드 워커에 재생한다
- **THEN** 매 회차 뒤의 물건, 변경 이력, 회차 기록, 수집 상태, 사진 기록과 파일 내용이 골든과 같다

#### Scenario: 차단 회차의 저장 결과
- **WHEN** 두 법원을 대상으로 한 회차에서 첫 법원은 정상, 두 번째 법원에서 차단 응답을 재생한다
- **THEN** 기존 수집기와 같게 그 회차의 물건은 저장되지 않고, 회차는 차단으로, 로테이션 위치는 두 번째 법원으로, 백오프는 1시간 뒤로 기록된다

### Requirement: 수집 운영 전환 보류와 동시 운영 금지
이 단계에서 운영 환경의 수집·사진 워커를 백엔드로 전환해서는 안 된다(MUST NOT). 운영 데이터가 아직 기존 데이터베이스에 있고, 백엔드 데이터베이스에는 시드만 있기 때문이다.

같은 외부 소스에 요청하는 두 수집 구현(기존 수집기와 백엔드 수집기)이 동시에 운영되어서는 안 된다(MUST NOT) — 두 구현은 서로 다른 데이터베이스의 백오프를 보지 못하고, 같은 IP의 요청 예산을 두 배로 쓴다. 전환은 기존 수집·사진 워커를 멈춘 뒤 데이터 이전과 함께 백엔드 워커를 켜는 순서로 해야 하며(SHALL), 그 절차는 문서로 남겨야 한다(SHALL).

개발 환경에서 실제 소스에 보내는 확인 요청은 1회 실행 방식의 최소 요청(물건 수집은 세션 초기화와 검색 첫 페이지, 사진은 세션 초기화와 상세 1건)으로 제한해야 하며(SHALL), 그 전에 기존 수집·사진 워커가 멈춰 있고 기존 백오프가 끝났음을 확인해야 한다(MUST).

#### Scenario: 운영 경로 유지
- **WHEN** 이 change를 적용한 뒤 기본 설정으로 운영 구성을 띄운다
- **THEN** 물건과 사진 수집은 기존 수집기가 기존 데이터베이스에 하고, 백엔드는 외부 소스에 요청하지 않는다

#### Scenario: 실제 소스 최소 확인
- **WHEN** 기존 수집·사진 워커를 멈추고 기존 백오프가 끝난 것을 확인한 뒤 백엔드를 1회 실행 방식으로 실제 소스에 한 번 실행한다
- **THEN** 실제 소스로 나간 요청은 물건 수집 2개, 사진 2개 이하이고, 결과가 수집 회차와 사진 회차 기록으로 남는다
