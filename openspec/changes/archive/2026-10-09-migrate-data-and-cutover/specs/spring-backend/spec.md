## ADDED Requirements

### Requirement: 운영 데이터 이전
기존 데이터베이스의 운영 데이터는 8개 테이블(`items`, `item_changes`, `analyses`, `worker_runs`, `bookmarks`, `feed_reads`, `collector_state`, `item_photos`) 전체를 백엔드 데이터베이스로 옮겨야 한다(SHALL). 운영 데이터이므로 시드와 달리 값을 가리거나 바꾸면 안 된다(MUST NOT). 시각·날짜·금액·JSON은 `금액과 시각의 정확한 저장` 요구사항의 표기로 바꾸되 같은 순간·같은 값이어야 한다(SHALL).

모든 행의 id는 원본과 같아야 한다(SHALL) — 물건 상세 주소, 외래 키, 사진 파일 경로(물건 id 디렉터리)가 id에 의존하기 때문이다. 이전 뒤 새로 만들어지는 행의 id는 원본에서 이미 쓰인 어떤 id(삭제된 행의 id 포함)와도 겹치면 안 된다(MUST NOT).

사진 기록이 가리키는 사진 파일은 백엔드 사진 디렉터리의 같은 상대 경로로 옮겨야 하며(SHALL), 바이트가 같아야 한다(SHALL). 사진 기록이 가리키지 않는 파일은 옮기지 않고 건수로 보고해야 한다(SHALL).

이전은 원자적이어야 한다(SHALL): 검증까지 끝나기 전에 실패하면 대상 데이터베이스에 이전한 행이 하나도 남으면 안 된다(MUST NOT). 대상 데이터베이스의 8개 테이블에 행이 있으면, 교체를 명시하지 않은 이전은 아무것도 쓰지 않고 거부해야 한다(SHALL). 같은 원본으로 교체 이전을 다시 실행하면 같은 결과가 나와야 한다(SHALL). 쓰기 없이 변환·적재·검증을 끝까지 해 보는 드라이런을 제공해야 한다(SHALL).

이전 과정의 출력과 산출물에는 원본 값이 들어갈 수 있으므로, 산출물은 저장소가 추적하지 않는 위치에만 써야 하고(SHALL), 표준 출력과 기록 문서에는 테이블 이름, 건수, 해시, 시간, 컬럼 이름만 남겨야 한다(SHALL).

#### Scenario: id 보존
- **WHEN** id 사이에 빈 번호가 있는 물건 데이터를 이전한 뒤 원본에 있던 물건 id로 물건 상세와 변경 이력을 조회한다
- **THEN** 원본과 같은 물건과 같은 변경 이력이 돌아온다

#### Scenario: 이전 뒤 새 행
- **WHEN** 원본에서 마지막 물건 행이 삭제되어 시퀀스가 최대 id보다 큰 상태로 이전한 뒤 새 물건을 저장한다
- **THEN** 새 물건의 id는 원본 시퀀스보다 크다

#### Scenario: 비어 있지 않은 대상
- **WHEN** 시드가 적재된 백엔드 데이터베이스에 교체를 명시하지 않고 이전을 실행한다
- **THEN** 이전은 대상 테이블과 건수를 알리며 거부되고, 대상 데이터베이스는 바뀌지 않는다

#### Scenario: 중간 실패
- **WHEN** 이전 도중 한 행이 대상 컬럼 제약을 어겨 적재가 실패한다
- **THEN** 대상 데이터베이스에는 이전 전 상태만 남고, 실패한 테이블과 컬럼 이름이 보고된다

#### Scenario: 드라이런
- **WHEN** 비어 있는 대상에 드라이런으로 이전을 실행한다
- **THEN** 행 수·해시 검증 결과가 보고되고, 대상 데이터베이스의 8개 테이블은 여전히 비어 있다

#### Scenario: 사진 파일
- **WHEN** 사진 기록 16건과 기록 없는 파일 1개가 있는 원본을 이전한다
- **THEN** 사진 파일 16개가 백엔드 사진 디렉터리의 같은 상대 경로에 같은 바이트로 생기고, 사진 파일 API로 내려받을 수 있으며, 기록 없는 파일 1건이 보고된다

### Requirement: 이전 결과 검증
이전은 테이블마다 행 수와, 행을 정해진 규칙으로 정규화해 직렬화한 값의 해시가 원본과 대상에서 같은지 확인해야 하며(SHALL), 하나라도 다르면 실패해야 한다(SHALL). 원본 쪽 값과 대상 쪽 값은 서로 다른 구현이 각자의 데이터베이스에서 계산해야 한다(SHALL) — 적재한 코드가 스스로를 검증하지 않게 하기 위해서다. 해시가 다르면 처음으로 다른 행의 키와 컬럼 이름을 보고해야 하며(SHALL), 값은 보고하면 안 된다(MUST NOT).

정규화 규칙은 원본과 대상 저장 방식의 차이 중 의미가 같은 것만 같게 만들어야 한다(SHALL): 시각은 밀리초 3자리 UTC 표기, 날짜는 `YYYY-MM-DD`, 정수는 10진 문자열, JSON은 키를 정렬한 표기, 그 밖의 문자열은 바이트 그대로.

이전 뒤에는 같은 요청을 기존 웹 앱 API(이전 원본)와 백엔드 API(이전 대상)에 보내 상태 코드와 본문이 같은지, 화면이 두 원천에서 같은지 확인해야 한다(SHALL). 물건 단위 읽기(상세, 변경 이력, 분석 이력, 사진 목록)는 모든 물건에 대해 확인해야 한다(SHALL).

#### Scenario: 해시 일치
- **WHEN** 원본을 이전한 뒤 검증한다
- **THEN** 8개 테이블의 행 수와 해시가 모두 같다고 보고된다

#### Scenario: 값 하나가 다름
- **WHEN** 대상의 변경 이력 한 행의 새 값을 바꾼 뒤 검증한다
- **THEN** 검증이 실패하고 그 행의 id와 컬럼 이름만 보고된다

#### Scenario: JSON 표기 차이
- **WHEN** 원본 회차 상세 JSON의 키 순서와 공백이 대상 데이터베이스가 저장한 표기와 다르다
- **THEN** 같은 값으로 판정된다

#### Scenario: 이전 뒤 API 비교
- **WHEN** 이전을 마친 뒤 모든 물건의 상세·변경 이력·분석 이력·사진 목록과 목록·관심·피드·회차 요청을 두 쪽에 보낸다
- **THEN** 모든 요청의 상태 코드와 본문이 같다

### Requirement: 이전 완료 표식과 수집 기동 조건
이전이 검증까지 성공하면 같은 원자적 단위 안에서 백엔드 데이터베이스에 이전 완료 표식(완료 시각과 원본 해시 요약)을 남겨야 한다(SHALL). 표식은 이전 결과 검증의 비교 대상에서 빠져야 한다(SHALL).

운영 프로필의 백엔드는 수집 또는 사진 주기 실행이 켜져 있는데 이전 완료 표식이 없으면 기동을 거부해야 하며(SHALL), 원인을 기동 로그에 남겨야 한다(SHALL) — 이전 전에 운영 구성을 띄워도 빈 데이터베이스로 실제 소스에 요청하지 않게 하기 위해서다. 시드·테스트·개발 프로필은 이 검사를 하지 않는다.

#### Scenario: 이전 전 운영 구성 기동
- **WHEN** 이전 완료 표식이 없는 데이터베이스로 운영 프로필 백엔드를 수집 주기 실행을 켜고 띄운다
- **THEN** 백엔드는 기동하지 않고, 외부 소스로 나간 요청이 없으며, 기동 로그에 이전 완료 표식이 없다고 남는다

#### Scenario: 이전 뒤 기동
- **WHEN** 이전을 성공한 데이터베이스로 같은 설정의 백엔드를 띄운다
- **THEN** 백엔드가 기동하고 수집·사진 주기 실행이 등록된다

### Requirement: 수집 운영 전환과 동시 운영 금지
같은 외부 소스에 요청하는 두 수집 구현(기존 수집기와 백엔드 수집기)이 동시에 운영되어서는 안 된다(MUST NOT). 운영 전환은 다음 순서로 해야 한다(SHALL): 기존 수집·사진 워커, 분석 워커, 화면 쓰기를 멈춤 → 진행 중 회차가 없음을 확인 → 기존 데이터베이스 백업 → 이전과 검증 → 백엔드 수집·사진 주기 실행과 외부 요청 허용을 켬 → 분석 워커의 서버 주소와 화면의 데이터 원천을 백엔드로 바꿈 → 첫 회차 확인. 차단 백오프 종료 시각과 로테이션 위치는 이전으로 그대로 이어져야 한다(SHALL).

백엔드 수집기의 첫 회차는 기존 수집기의 마지막 회차가 끝난 뒤 수집 주기 이상 지난 뒤에 시작해야 하며(SHALL), 이전된 백오프가 남아 있으면 건너뛰어야 한다(SHALL). 전환 동안 기존 수집기의 마지막 회차 종료부터 백엔드 수집기의 첫 회차 시작까지의 수집 공백을 기록해야 한다(SHALL).

실제 운영 전환은 실제 소스에 요청이 생기므로 사람이 사전 확인을 마친 뒤 실행해야 하며(SHALL), 그 전에 운영 데이터 복사본과 가짜 소스로 같은 절차의 전환과 롤백을 개발 환경에서 리허설해야 한다(SHALL). 리허설은 실제 소스에 요청해서는 안 된다(MUST NOT).

#### Scenario: 전환 뒤 운영 구성
- **WHEN** 전환을 마친 운영 구성을 띄운다
- **THEN** 물건과 사진 수집은 백엔드만 하고, 기존 수집·사진 워커는 실행되지 않으며, 화면과 분석 워커는 백엔드 API만 쓴다

#### Scenario: 이전된 백오프
- **WHEN** 기존 수집기가 차단으로 1시간 백오프를 건 직후 전환하고 백엔드 수집 주기가 도래한다
- **THEN** 외부 요청 없이 사유가 백오프인 건너뜀 회차가 기록된다

#### Scenario: 리허설
- **WHEN** 운영 데이터 복사본과 가짜 소스 서버로 전환과 롤백을 리허설한다
- **THEN** 이전 검증과 API 비교가 일치하고, 백엔드 첫 회차가 가짜 소스로만 요청하며, 롤백 뒤 기존 경로가 복사본 데이터로 다시 동작한다

### Requirement: 롤백 창
전환 뒤 정해진 롤백 창 동안에는 기존 경로로 되돌릴 수 있어야 한다(SHALL). 롤백 창 동안 전환 직전의 기존 데이터베이스 백업과 기존 데이터 볼륨을 지우거나 바꾸면 안 되며(MUST NOT), 기존 경로의 코드와 구성은 저장소에서 다시 쓸 수 있어야 한다(SHALL).

롤백은 백엔드 수집·사진 주기 실행을 끄고 분석 워커와 화면 쓰기를 멈춘 뒤 기존 경로를 전환 직전 상태로 되돌리는 것이다. 전환 뒤 백엔드 데이터베이스에 생긴 데이터는 기존 데이터베이스로 옮기지 않으며, 테이블별로 생긴 건수를 롤백 전에 기록해야 한다(SHALL). 단 백엔드에 저장된 차단 백오프 종료 시각이 기존 데이터베이스의 값보다 늦으면 그 값을 기존 데이터베이스에 써야 하고(SHALL), 로테이션 위치도 백엔드의 값으로 써야 한다(SHALL) — 되돌린 수집기가 차단 중인 소스에 요청하지 않게 하기 위해서다.

SQLite 구현체와 기존 경로 코드의 은퇴는 롤백 창이 끝나고 사람이 확인한 뒤에만 해야 한다(SHALL).

#### Scenario: 롤백 창 안의 롤백
- **WHEN** 전환 뒤 백엔드에 물건 변경 이력과 분석이 쌓이고 백엔드 수집기가 차단으로 백오프를 건 상태에서 롤백한다
- **THEN** 생긴 건수가 테이블별로 기록되고, 기존 데이터베이스에는 전환 직전 데이터와 백엔드의 백오프 종료 시각·로테이션 위치만 반영되며, 기존 수집기는 백오프가 끝날 때까지 요청하지 않는다

#### Scenario: 롤백 창 종료 전 은퇴 금지
- **WHEN** 롤백 창이 끝나기 전에 은퇴 작업을 시작하려 한다
- **THEN** 작업 목록의 사람 확인 단계가 완료되지 않아 은퇴를 진행하지 않는다

### Requirement: 계약 골든 동결
기존 웹 앱 API와 기존 수집기로 만든 계약 골든(읽기 계약, 쓰기·화면용 시나리오, 소스 어댑터, 수집 저장)은 기존 경로가 은퇴한 뒤에도 저장소에 남아 백엔드 테스트의 기준이어야 한다(SHALL). 은퇴 뒤에는 골든을 다시 생성할 수 없으므로, 골든 파일을 바꾸는 변경은 바꾸는 이유를 그 변경의 설계 문서에 남겨야 한다(SHALL). 백엔드 테스트는 골든을 읽기만 하고 고쳐 쓰면 안 된다(MUST NOT).

#### Scenario: 은퇴 뒤 계약 테스트
- **WHEN** 기존 경로를 은퇴시킨 뒤 백엔드 테스트를 실행한다
- **THEN** 읽기 계약, 시나리오, 어댑터, 저장 골든 테스트가 은퇴 전과 같은 개수로 통과한다

## MODIFIED Requirements

### Requirement: 컨테이너 기반 실행
`docker compose`로 MySQL과 백엔드를 함께 띄울 수 있어야 한다(SHALL). 백엔드는 MySQL이 요청을 받을 수 있게 된 뒤에 시작해야 하며(SHALL), 데이터베이스 데이터와 사진 파일은 컨테이너를 지웠다 다시 만들어도 볼륨에 남아야 한다(SHALL). 접속 정보 같은 비밀 값은 이미지나 저장소에 고정되지 않고 환경 변수로 주입되어야 한다(MUST).

운영 구성의 백엔드는 시드를 적재하지 않는 운영 프로필로 실행해야 하며(SHALL), 접속 정보가 비어 있으면 기본값으로 대신 접속하지 않고 기동에 실패해야 한다(SHALL). 시드를 적재하는 구성(스모크 확인, 개발 스크립트)은 운영 구성과 다른 파일이나 덮어쓰기로 띄워야 하며(SHALL), 그 구성은 수집·사진 주기 실행과 외부 요청 허용을 켜면 안 된다(MUST NOT).

#### Scenario: 처음 기동
- **WHEN** 빈 상태에서 스모크 구성으로 MySQL과 백엔드를 띄운다
- **THEN** MySQL이 준비된 뒤 백엔드가 시작되고, 헬스체크가 200을 돌려주며, 목록 API가 시드 데이터를 돌려주고, 수집·사진 회차가 실행되지 않는다

#### Scenario: 재기동 후 데이터 유지
- **WHEN** 컨테이너를 내렸다가 볼륨을 지우지 않고 다시 띄운다
- **THEN** 이전 데이터와 사진 파일이 그대로 조회되고 시드가 중복 적재되지 않는다

#### Scenario: 기존 경로 무영향
- **WHEN** 운영 구성이 쓰는 호스트에서 스모크 구성을 띄웠다가 볼륨까지 지우며 내린다
- **THEN** 운영 구성의 MySQL 볼륨과 사진 볼륨은 바뀌지 않는다

#### Scenario: 운영 프로필의 접속 정보 누락
- **WHEN** 데이터베이스 비밀번호 없이 운영 프로필 백엔드를 띄운다
- **THEN** 백엔드는 기동에 실패하고, 기본 계정으로 접속을 시도하지 않는다

### Requirement: 분석 워커 무수정 연결
분석 워커는 코드 수정 없이 실행 설정(서버 주소)만 바꿔 백엔드와 동작해야 한다(SHALL). 백엔드에 연결된 분석 워커의 한 회차는 대상 조회, 분석 결과 저장, 회차 시작·종료 기록을 모두 백엔드 API로 처리해야 하며(SHALL), 결과는 백엔드의 데이터베이스에 남아야 한다(SHALL).

운영 구성의 분석 워커는 서버 주소로 백엔드를 써야 한다(SHALL). 분석 워커 코드는 운영 전환을 위해 바뀌면 안 된다(MUST NOT) — 운영 전환 전후 분석 워커 코드의 차이는 0줄이어야 한다.

#### Scenario: 주소만 바꾼 분석 회차
- **WHEN** 개발 환경에서 분석 워커를 백엔드 주소로 1회 실행한다(분석 모델 호출은 가짜 실행 파일로 대체)
- **THEN** 백엔드 데이터베이스에 새 분석이 저장되고 분석 회차 기록이 성공으로 남으며, 분석 워커 코드의 변경은 0줄이다

#### Scenario: 운영 경로 유지
- **WHEN** 운영 전환을 마친 운영 구성으로 분석 워커를 띄운다
- **THEN** 분석 워커의 운영 경로는 백엔드다: 분석 워커는 백엔드 주소로 통신하고, 분석과 회차 기록은 백엔드 데이터베이스에 저장되며, 전환 전후 분석 워커 코드의 차이는 0줄이다

### Requirement: 수집 스케줄러 기본 꺼짐과 외부 요청 차단
수집 워커와 사진 워커의 주기 실행은 백엔드 설정의 기본값으로 꺼져 있어야 한다(SHALL). 각 워커를 켜는 설정을 명시하지 않은 백엔드는 주기 실행을 등록해서는 안 되며(MUST NOT), 기동 로그에 켜짐·꺼짐을 남겨야 한다(SHALL).

외부 소스로 나가는 요청은 외부 요청 허용 설정을 명시하지 않으면 보내서는 안 된다(MUST NOT). 허용되지 않은 상태에서 루프백이 아닌 주소로 요청하려 하면 네트워크에 나가지 않고 요청 실패로 끝나야 한다(SHALL) — 주기 실행 설정이 실수로 켜져도 외부 사이트를 부르지 않게 하는 두 번째 잠금이다.

자동 테스트와 CI는 외부 사이트에 요청해서는 안 된다(MUST NOT). 소스 요청을 다루는 테스트는 루프백의 가짜 서버만 상대해야 한다(SHALL). 주기 실행을 켜는 곳은 운영 배포 구성(Docker Compose 운영 구성, Kubernetes 백엔드 워크로드)뿐이어야 한다(SHALL). 외부 요청 허용을 켜는 곳은 운영 배포 구성과, 기존 수집기를 멈춘 뒤 사람이 실행하는 실제 소스 최소 확인용 1회 실행 절차뿐이어야 한다(SHALL). 스모크·개발용 구성과 리허설 구성은 두 설정 중 외부 요청 허용을 켜면 안 된다(MUST NOT). 1회 실행 모드는 배포 구성에 두면 안 된다(MUST NOT).

#### Scenario: 기본 설정으로 기동
- **WHEN** 수집 관련 설정 없이 백엔드를 기동하고 수집 주기보다 오래 기다린다
- **THEN** 수집·사진 회차가 하나도 실행되지 않고, 외부로 나간 요청이 없으며, 기동 로그에 두 워커가 꺼져 있다고 남는다

#### Scenario: 외부 요청 허용 없이 실제 주소
- **WHEN** 외부 요청 허용 설정 없이 소스 주소를 루프백이 아닌 주소로 두고 회차를 실행한다
- **THEN** 네트워크 요청이 나가지 않고 그 회차가 요청 실패로 기록되며, 차단 백오프는 걸리지 않는다

#### Scenario: 배포 구성
- **WHEN** 운영 배포 구성과 스모크·개발용 구성의 백엔드 설정을 확인한다
- **THEN** 운영 배포 구성의 백엔드만 수집·사진 주기 실행과 외부 요청 허용을 켜고, 스모크·개발용·리허설 구성은 외부 요청 허용을 켜지 않으며, 어느 배포·스모크 구성에도 1회 실행 모드가 없다

## REMOVED Requirements

**Migration**: "수집 운영 전환과 동시 운영 금지"와 "롤백 창" 요구사항을 따른다.
