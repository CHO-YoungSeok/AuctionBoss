# Proposal: scale-collection-scheduling

## Why

수집 범위가 서울중앙지방법원 1곳에 묶여 있다. 전국 60개 법원으로 넓히는 것이 원래 목표였지만, **지금 구조로는 불가능하다**:

- 회차당 요청 = 쿠키 1회 + 페이지 N회. 서울중앙 2개월 범위가 444행 / 페이지 상한 40 → 12페이지 → **13요청**(`NOTES.md` §6.1, 실측).
- 실제 차단을 유발한 임계는 **5분에 15회 미만**(실측). 지금도 임계에 근접해 있다.
- 법원을 늘리면 요청이 법원 수에 비례한다. 60곳이면 수백 요청이 되어 즉시 차단이다.

즉 "전국 확대"의 선행 조건은 법원을 추가하는 코드가 아니라 **요청량을 통제하면서 여러 법원을 순회하는 방법**이다. 지금 어댑터는 설정된 모든 법원을 한 회차에 전부 돈다 — 법원을 2곳만 추가해도 요청이 배로 뛴다.

3회차에서 회차 기록을 만들어 **실제 요청 페이지 수가 남기 시작했다.** 이제 추측이 아니라 실측으로 안전한 예산을 정할 수 있다.

## What Changes

- **회차당 요청 예산**을 설정으로 둔다. 한 회차가 보낼 수 있는 요청 수의 상한이며, 예산을 넘기면 그 회차는 남은 법원을 다음 회차로 미룬다.
- **법원 로테이션**: 설정된 법원 전체를 매 회차 다 돌지 않고, 예산 안에서 일부만 돈다. 다음 회차는 그 다음 법원부터 이어서 돈다. 모든 법원이 순환하면서 공평하게 수집되어야 하며, 특정 법원이 영구히 뒤로 밀려서는 안 된다.
- 로테이션 진행 위치를 저장해 워커를 재시작해도 이어서 돈다. 재시작할 때마다 처음부터 돌면 뒤쪽 법원은 영원히 수집되지 않는다.
- **한 바퀴 도는 데 걸리는 시간**(전체 법원을 한 번씩 수집하는 주기)을 계산해 상태 화면에 보여준다. 법원을 추가할 때 신선도가 얼마나 나빠지는지 사전에 알 수 있어야 한다.
- 차단 백오프는 **전체 로테이션에 적용**한다. 한 법원에서 차단됐다고 다른 법원으로 계속 요청하면 차단이 길어진다.
- 회차 기록에 이번 회차가 어떤 법원을 돌았는지 남긴다(3회차의 `detail`에 이미 대상 법원 필드가 있다).
- 설정에 법원을 추가하는 방법과 그때의 트레이드오프(신선도 저하)를 문서화한다.

**BREAKING 아님**: 법원이 1곳뿐이면 지금과 동일하게 동작해야 한다. 기존 설정 파일이 그대로 유효해야 한다.

비목표(후속): 상용 API 어댑터(별도 계약·비용 검토 필요), 법원별 다른 주기, 물건 변동 빈도에 따른 적응형 스케줄링, 실제 60개 법원 전체 활성화(이 change는 그것이 **가능해지는** 구조를 만들고, 실제 확대는 실측 후 판단).

## Capabilities

### New Capabilities

(없음)

### Modified Capabilities

- `auction-collection`: "수집 범위 설정"과 "주기적 수집 실행" 요구사항에 요청 예산과 법원 로테이션이 추가된다. "수집 실패 처리"의 차단 백오프가 로테이션 전체에 적용됨을 명시한다.
- `run-observability`: 회차 기록에 로테이션 상태(이번 회차 대상 법원, 한 바퀴 진행률)가 포함되고, 상태 화면에 한 바퀴 소요 시간이 표시된다.

## Impact

- `config/collector.json`에 요청 예산 설정 추가. 법원 목록은 이미 배열이다.
- 로테이션 위치를 저장할 곳이 필요하다. 새 테이블을 만들 만한 규모가 아니므로 저장 방식을 설계에서 정한다.
- `workers/collector.ts`의 회차 실행이 "전체 법원"에서 "예산 안의 일부 법원"으로 바뀐다. 어댑터의 `fetchActiveItems(scope)`는 이미 scope를 받으므로 계약 변경은 없을 것으로 보이나 확인이 필요하다.
- 상태 화면에 한 바퀴 소요 시간 표시.
- **기존 동작 보존이 핵심 위험**: 법원 1곳 설정에서 지금과 다르게 동작하면 회귀다. 회귀 테스트로 고정한다.
