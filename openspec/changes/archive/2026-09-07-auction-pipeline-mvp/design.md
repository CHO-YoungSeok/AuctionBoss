# Design: auction-pipeline-mvp

## Context

빈 저장소에서 시작하는 신규 프로젝트다(동기는 proposal.md 참조). 외부 제약:

- 법원경매정보(courtauction.go.kr)는 공식 Open API가 없다. 2024년 개편된 사이트는 프론트가 내부 엔드포인트에 POST로 JSON을 요청해 화면을 그리는 구조이므로, HTML 파싱 없이 JSON 응답을 파싱하는 방식으로 수집한다. 단, 비공식 엔드포인트라 예고 없이 바뀔 수 있다.
- 분석은 서버 로컬에 설치·인증된 Claude Code CLI(headless, `claude -p`)로 실행한다. 호출당 비용이 있으므로 분석 건수 통제가 필요하다.

## Goals / Non-Goals

**Goals:**
- 수집 → 저장 → 열람 → 분석 → 결과 표시의 엔드투엔드 흐름이 실제로 도는 최소 구조
- 소스 교체(어댑터)와 분석 고도화(워커 격리)가 이후 change에서 국소 변경으로 가능하도록 경계 설정

**Non-Goals:**
- 분석 프롬프트 품질, 상용 데이터 소스, 전국 규모 수집 성능, 인증/권한, 배포 자동화

## Decisions

### D1. 모노레포 구조: Next.js 앱 + 워커 스크립트 동거

하나의 저장소, 하나의 package.json으로 시작한다.

```
/src
  /app            # Next.js App Router (페이지 + /api 라우트)
  /lib
    /db           # SQLite 접근 (better-sqlite3), 스키마/마이그레이션
    /domain       # AuctionItem, Analysis 등 정규화 모델 타입
    /sources      # AuctionSource 인터페이스 + CourtAuctionAdapter
/workers
  collector.ts    # 10분 주기 수집 (node로 상주 실행)
  analyzer.ts     # 미분석 물건 조회 -> claude -p 실행 -> POST /api/analyses
/config
  collector.json  # 수집 범위(법원 코드), 주기, 분석 회차당 최대 건수
```

- 왜: 1단계에서 패키지 분리는 오버헤드만 크다. 워커는 Next.js 서버와 별개 프로세스로 실행하되(`npm run collector`, `npm run analyzer`) 코드는 `/src/lib`을 공유한다.
- 대안(고려 후 기각): pnpm workspace 모노레포 — 배포 단위가 나뉠 때 도입해도 늦지 않다.

### D2. DB: SQLite(better-sqlite3) + 두 테이블

- `items`: 정규화 물건. UNIQUE(court, case_no, item_no). `first_seen_at`, `last_seen_at` 컬럼으로 신규/갱신 구분.
- `analyses`: 분석 결과. `item_id` FK, `body`(markdown), `model`, `prompt_version`, `analyzed_at`. 물건당 여러 행 허용(최신 것을 표시) — 재분석 기능이 후속으로 와도 스키마 변경이 없다.
- 왜 better-sqlite3: 동기 API라 워커 스크립트가 단순해지고, 이 규모(지역 1곳, 수백 건)에서 성능 문제가 없다. ORM(Prisma/Drizzle)은 1단계에서 배제 — 테이블 2개에 도구 학습·설정 비용이 더 크다.

### D3. AuctionSource 어댑터 계약

```ts
interface AuctionSource {
  fetchActiveItems(scope: CollectScope): Promise<AuctionItem[]>;
}
```

- 어댑터가 정규화까지 책임진다. 반환 타입은 `/lib/domain`의 `AuctionItem`이며 소스 원본 형식은 어댑터 밖으로 나가지 않는다.
- `CourtAuctionAdapter`는 내부 JSON 엔드포인트에 물건 검색 POST를 보내고 페이지네이션을 순회한다. 응답은 zod 스키마로 검증해 형식 변경을 파싱 시점에 감지한다(조용한 실패 방지 — spec의 수집 실패 처리 요구사항).
- 실제 엔드포인트 URL·파라미터는 구현 시점에 사이트를 직접 관찰해 확정한다(개발 중 변할 수 있는 세부라 여기 고정하지 않음).

### D4. 수집 스케줄: 프로세스 내 setInterval, 중첩 방지 플래그

- cron(OS)이 아니라 상주 워커 안에서 10분 타이머로 실행. 왜: 실행 중 여부를 프로세스 메모리로 알 수 있어 "이전 수집 미완료 시 건너뛰기" 요구사항이 단순해지고, 로컬 개발에서 켜고 끄기 쉽다.
- 대안(기각): OS cron — 중첩 방지에 lock 파일이 필요해지고 로그가 흩어진다.

### D5. Analyzer는 HTTP로만 서버와 통신

- 분석 워커는 DB를 직접 읽지 않는다. `GET /api/items?analyzed=false&pageSize=N`으로 대상을 받고, `POST /api/analyses`로 결과를 넣는다.
- 왜: "서버 로컬에서 돌리고 결과를 서버로 공유"라는 요구를 API 경계로 구현하면, 나중에 분석기를 다른 머신으로 옮기거나 여러 대로 늘려도 서버는 그대로다. 분석 프롬프트 발전이 서비스 본체 코드와 완전히 분리된다.
- Claude Code 실행: `claude -p "<물건 데이터를 포함한 분석 프롬프트>" --output-format json`을 child_process로 호출. 프롬프트 템플릿은 `workers/prompts/analyze-item.md`에 두고 `prompt_version` 문자열(예: `v1`)을 결과에 기록한다 — 이후 프롬프트를 바꿀 때 어떤 버전으로 분석된 결과인지 추적하기 위함.
- 1단계 분석 주기: collector와 별도로 10분 주기 상주 실행, 회차당 최대 건수 기본 5건.

### D6. 로봇탐지 대응 (태스크 3.1 조사 후 추가)

조사(`src/lib/sources/courtauction/NOTES.md` §6.1)에서 확인된 사실: 사이트에 IP 단위 로봇탐지가 있고, 5분 내 15회 미만 요청으로도 차단됐으며 최소 13분 이상 지속됐다. 차단 시에도 **HTTP 200**으로 응답하고 본문만 `{"data":{"ipcheck":false}}`로 바뀐다. 별도 WAF는 브라우저가 아닌 User-Agent에 HTML 차단 페이지를 200으로 반환한다.

따라서:

- 응답 판정은 HTTP 상태 코드가 아니라 **본문 3단 검사** 순서로 한다: (1) 본문이 `{`로 시작하는가(아니면 WAF HTML), (2) `data.ipcheck === true`인가, (3) zod로 `data.dlt_srchResult` 스키마 검증.
- 요청 수를 줄이기 위해 페이지 크기를 최대로 잡고, 페이지 사이에 수 초 sleep을 둔다. 동시 요청은 금지.
  - **실측 정정(태스크 3.2 구현 중 확인)**: 서버가 받는 `pageSize` 상한은 **40**이다. 100을 보내면 HTTP 400으로 거부되고, UI가 제공하는 선택지도 10/20/30/40뿐이다. 따라서 상한 겸 기본값은 40이며, 설정이 그보다 크면 경고 후 클램프한다.
  - 이 상한 때문에 서울중앙 2개월 범위(444행)는 한 회차에 쿠키 1회 + 페이지 12회 = **약 13요청**이 필요하다. 조사에서 차단이 발생한 수준(5분에 15회 미만)에 근접하므로, **10분 주기 상시 운용의 지속 가능성은 아직 검증되지 않았다.** 실운영 전 관측이 필요하며, 차단이 반복되면 (a) 수집 주기를 늘리거나 (b) `bidWindowDays`를 줄여 행 수를 낮추는 것이 1차 대응이다.
- 차단이 감지되면 그 회차를 즉시 중단하고 **장시간 백오프**(기본 1시간)를 걸어 다음 주기 tick들을 건너뛴다. 쿠키 재발급으로는 풀리지 않으므로 재시도는 무의미하다.
- 이는 spec의 "수집 실패 처리"(실패를 조용히 넘기지 않고 로그+회차 중단, 다음 주기 정상 시도)를 만족하되, 차단에 한해 다음 주기를 건너뛴다는 점만 확장한 것이다. 백오프 없이 10분마다 재시도하면 차단이 영구화될 수 있다.
- `robots.txt`는 404(명시적 금지 지시자 없음). 이용약관 검토는 외부 서비스로 데이터를 제공하기 전에 별도로 수행한다.

### D7. 수집 범위 설정

`/config/collector.json`에 법원 코드 목록(기본: 1곳), 수집 주기(ms), 분석 회차당 최대 건수를 둔다. 환경 변수가 아닌 파일인 이유: 법원 코드처럼 목록형 설정이 들어가고, 이후 지역 확장이 파일 한 줄 추가가 되게 하기 위함.

## Risks / Trade-offs

- [비공식 엔드포인트 변경으로 수집 전면 중단] → zod 검증으로 즉시 감지·로그, 어댑터에 국소화되어 수정 범위가 좁다. 장기적으로 상용 데이터 어댑터를 대안으로 준비.
- [자동 수집이 사이트 이용약관과 충돌할 소지] → 지역 1곳·10분 주기로 요청량 최소화. 외부 서비스로 데이터를 재판매하기 전에 법적 검토 필요(현 단계는 개인/내부 열람 용도).
- [로봇탐지로 IP가 장시간 차단되어 수집이 멈춤] → D6의 3단 검사와 백오프로 대응. 그래도 10분 주기가 지속 가능한지는 실측이 필요하며(조사 시 5분 15회 미만으로도 차단), 차단이 반복되면 주기를 늘리거나 상용 데이터 소스로 전환하는 것이 근본 대안이다.
- [Claude 분석 비용 폭증] → 회차당 최대 건수 설정 + 신규 물건만 분석. 재분석은 후속 change에서 명시적 트리거로만.
- [SQLite 동시 쓰기 한계] → 쓰기 주체가 collector와 API 서버(analyses 저장) 둘뿐이고 빈도가 낮아 WAL 모드로 충분. 규모 확장 시 Postgres 이전(도메인 모델이 분리되어 있어 이전 비용 낮음).
- [워커 프로세스가 죽으면 수집·분석 중단] → 1단계는 수동 재시작 허용. 로그에 시작/종료를 남겨 감지 가능하게 함. 프로세스 매니저(pm2 등)는 배포 단계에서 도입.

## Open Questions

- **`yuchalCnt`와 `minBidPrice`가 어긋나는 행이 있다** (6.1 E2E 중 AI 분석이 지적). 실제 수집된 물건에서 `yuchalCnt=1`인데 최저매각가격이 감정가와 같은(100%) 경우가 관측됐다. 가능한 원인은 (a) 유찰 후 기일변경·재감정으로 가격이 리셋됨, (b) `notifyMinmaePrice1`/`minmaePrice` 폴백 선택이 부적절함, (c) `yuchalCnt`가 현재 기일이 아닌 사건 전체 이력을 센다 — 셋 다 미검증이다. 파생값인 `status`("유찰 N회")의 정확도에 직접 영향을 주므로, 물건 상세 엔드포인트(`selectAuctnCsSrchRslt.on`)를 붙일 때 함께 확인할 것.
- 목록 화면의 필터(용도별, 가격대별)는 어떤 것부터 붙일지 — 1단계 이후 사용해보고 결정해도 스펙·구조에 영향 없음.
- 분석 프롬프트에 어떤 외부 정보(시세, 등기부 등)를 결합할지 — Analyzer 내부에서만 발전시키면 되는 영역.
