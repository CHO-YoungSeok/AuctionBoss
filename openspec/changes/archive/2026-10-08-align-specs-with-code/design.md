## Context

- 동기와 범위는 proposal.md를 따른다.
- 메인 스펙 9개를 코드와 대조한 결과(2026-10-08), 높음 7건, 중간 16건, 낮음 26건의 불일치가 나왔다. 아카이브된 change 18개의 delta는 메인 스펙에 빠짐없이 병합돼 있었다. 즉 불일치는 병합 실수가 아니라, 나중 change가 코드나 설정만 바꾸고 스펙을 고치지 않아서 생겼다.
- 불일치는 두 종류다. 코드는 의도대로인데 스펙이 낡은 경우와, 스펙은 옳은데 코드가 요구사항을 지키지 못한 경우다. 이 change는 앞의 것만 다룬다.

## Goals / Non-Goals

**Goals:**
- 고친 뒤의 메인 스펙이 현재 코드의 실제 동작과 같아서, 다음 change(쓰기 API 이식, 사진 워커 수정)가 이 스펙을 계약으로 믿을 수 있다.
- 스펙 안의 모순(같은 대상을 두 가지로 말하는 곳)을 없앤다.

**Non-Goals:**
- 코드, 설정, 테스트 변경.
- 스펙은 옳고 코드가 틀린 경우의 수정(사진 워커 회차 기록·백오프 공유·재시도 간격·어댑터 우회, 배포 설정의 분석 워커 주소 변수, Next 이미지 헬스체크). 이 요구사항들은 지금 문구를 그대로 두고, 코드를 고치는 후속 change에서 다룬다.
- 표현만의 문제(빈 줄, 오타, change 시점 말투)와 메인 스펙 Purpose 문구 정리. Purpose는 delta로 고칠 수 없어서 별도로 직접 고친다(tasks 참고).

## Decisions

### D1. 스펙을 고칠지 코드를 고칠지 가르는 기준
- **스펙을 고친다**: 코드 동작이 의도된 것이고, 그 동작을 지키는 테스트가 있으며, 스펙만 그 의도를 반영하지 못한 경우. 예: 화면의 분석 최신성 판정에서 쿨다운을 빼는 것은 테스트가 "의도된 차이"로 고정하고 있다.
- **코드를 고친다**: 스펙이 요구하는 동작이 서비스에 필요하고, 코드가 그것을 구현하지 않았거나 체크리스트만 완료로 표시된 경우. 예: 사진 워커의 차단 백오프 공유는 수집 차단을 막는 핵심 안전장치라서 스펙을 낮추지 않는다.
- **버린 대안**: 모든 불일치를 스펙 쪽으로 맞추기. 빠르지만 "구현하지 못한 것을 요구사항에서 지우는" 셈이라, 스펙이 기준 역할을 잃는다.

### D2. 근거를 코드에서 다시 확인한 뒤 쓴다
- 검증 보고서를 그대로 옮기지 않고, 고칠 문장마다 근거 코드 위치와 그 동작을 지키는 테스트를 다시 연다. 보고서와 코드가 다르면 코드 기준으로 쓴다.

### D3. MODIFIED는 요구사항 블록 전체를 옮긴다
- OpenSpec은 MODIFIED 블록으로 메인 요구사항을 통째로 바꾼다. 일부만 적으면 아카이브 때 나머지 시나리오가 사라진다. 그래서 블록 전체를 복사해 고치고, 메인 원문과 diff해서 의도한 문장 외에는 바뀌지 않았는지 확인한다.
- 요구사항 이름 변경("Claude Code 분석 실행" → "Claude 분석 실행")은 RENAMED로 따로 적는다.

## Risks / Trade-offs

- [MODIFIED 블록 복사 중 시나리오가 빠지면 아카이브 때 요구사항이 조용히 사라짐] → 블록마다 메인과 diff하고, 아카이브 전후로 요구사항과 시나리오 개수를 비교한다.
- [스펙을 코드에 맞추다가 버그까지 정상으로 굳힘] → D1 기준으로 가르고, 애매한 것은 스펙을 고치지 않고 후속 코드 수정 목록에 남긴다.
- [스펙만 바뀌므로 게이트로는 검증되지 않음] → 고친 문장마다 근거 코드와 테스트를 대조한 표를 tasks 검증에 남긴다.

## Migration Plan

문서만 바뀐다. 아카이브할 때 메인 스펙 7개가 갱신되고, 되돌리려면 그 커밋을 되돌리면 된다.
