# Design: enrich-item-fields

## Context

동기는 proposal.md 참조. 조사로 확정된 사실(`src/lib/sources/courtauction/NOTES.md`):

- §3.1과 §8의 실제 응답, 그리고 `__tests__/fixtures.ts`의 `REAL_ROW`에 확장 필드들이 **CONFIRMED**로 존재한다. `schema.ts`의 zod 스키마가 선언하지 않아 파싱 단계에서 버려질 뿐이다.
- §10.5: 상세 엔드포인트는 물건당 1요청 = 회차당 402요청으로 차단 임계의 약 27배다. 이번 change는 **추가 요청 0건**이다.
- §10.3: 권리관계·임차인 데이터는 이 소스에 **존재하지 않는다**(CONFIRMED 부재). 분석 품질의 상한이 여기서 정해진다.
- 좌표계(EPSG)와 `jinstatCd`/`mulStatcd` 코드표는 **UNVERIFIED**로 남아 있다.

기존 구조에서 이번 작업에 영향을 주는 것:

- `items` 테이블은 `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN` 마이그레이션 패턴을 이미 쓴다(`item_changes.kind` 선례).
- `WATCHED_FIELDS`가 변경 이력과 재분석을 구동한다. 여기에 필드를 넣으면 기존 물건 전체가 "변경됨"이 된다.
- 프롬프트 버전을 올리면 분석된 모든 물건이 재분석 대상이 된다(아카이브된 `add-price-change-history` D4). 재분석 한도와 쿨다운이 속도를 제한한다.
- `renderItemPrompt`가 `AuctionItem` 전체를 `JSON.stringify`해서 프롬프트에 주입한다 — 필드를 추가하면 자동으로 분석 입력에 들어간다.

## Goals / Non-Goals

**Goals:**
- 이미 받고 있는 데이터를 버리지 않기 (추가 요청 0건)
- 확장 필드가 없어도 기존 동작이 그대로일 것
- 값 없음과 값 0을 구별
- 의미를 모르는 코드값을 해석하지 않고 원문 보존

**Non-Goals:**
- 상세 엔드포인트, 사진, 감정평가서 (NOTES §10.6이 권장하지 않는다)
- 면적·좌표 기반 필터·정렬·지도 (표시와 분석 입력까지만)
- 코드표 해석 — 코드표를 모르므로 추측하면 틀린 정보가 된다

## Decisions

### D1. `items`에 컬럼 추가. 새 테이블 없음

확장 필드는 전부 물건당 스칼라 값 1개다. 정규화할 이유가 없다.

- 예외 후보였던 **차수별 최저가**(1~4차)도 컬럼으로 둔다. 소스가 고정 4개 슬롯(`notifyMinmaePrice1..4`)으로 주므로 가변 배열이 아니고, 별도 테이블은 조인만 늘린다. 회차 수가 가변이 되는 날 옮긴다.
- 모든 새 컬럼은 **nullable**. 기존 행은 NULL로 남고 다음 수집 때 채워진다. 이 change의 마이그레이션은 값을 소급하지 않는다 — 소급할 데이터가 없다.
- 마이그레이션은 `item_changes.kind` 때와 같은 방식(`ALTER TABLE ADD COLUMN`, `IF NOT EXISTS` 패턴 유지)으로 하고, 변경 전 스키마로 만든 DB 파일을 새 코드로 여는 테스트를 반드시 둔다.

### D2. `WATCHED_FIELDS`를 늘리지 않는다

새 필드를 감시 대상에 넣으면 **기존 물건 전체가 다음 수집에서 "변경됨"으로 기록**된다(현재 값이 NULL이고 새로 값이 들어오므로 `null → 값` = 실제 변경). 그러면:

- `item_changes`에 물건 수 × 필드 수만큼 행이 한 번에 쌓인다
- 그 물건들이 전부 재분석 대상이 된다 — 프롬프트 v2로 인한 재분석과 겹쳐 이중으로 유발된다

감시 대상 확대는 "무엇이 실제로 의미 있는 변화인가"를 실데이터로 본 뒤 결정할 별도 판단이다. 이번에는 손대지 않는다. (차수별 최저가는 감시 대상 후보로 유력하지만, 1차 최저가가 이미 감시 대상이라 중복 신호가 될 수 있어 관측이 먼저다.)

### D3. 값 없음의 표현: `null`, 그리고 `0`과 구별

소스는 값이 없을 때 `""` 또는 `"0"`을 보낸다(기존 `text()`/`toInt()` 헬퍼가 이미 `""` → `null` 처리를 한다).

- 가격·면적·회차 같은 수치는 **`0`을 유효값으로 취급하지 않는다** — 이 도메인에서 최저가 0원이나 면적 0㎡는 "값 없음"이지 실제 0이 아니다. 기존 `pickMinBidPrice`가 이미 0을 폴백 트리거로 쓰고 있어 선례가 있다.
- 단, **유찰횟수 0은 유효값**이다(신건). 수치라고 일괄 처리하면 안 되므로 필드별로 정한다.
- 이 규칙은 도메인 타입에 `| null`로 드러내고, 표시 계층이 없음을 "-"로 렌더한다.

### D4. 의미를 모르는 코드값은 원문만 저장

`jinstatCd`, `mulStatcd`, `bidDvsCd`, 용도 3단계 코드, 좌표계 불명의 `xCordi`/`yCordi`가 여기 해당한다.

- 컬럼명은 도메인 이름(camelCase)으로 두되, **해석하지 않고 문자열 그대로** 저장한다.
- 화면에는 코드값을 그대로 노출하거나 아예 표시하지 않는다. 추측한 라벨을 붙이면 틀린 정보가 사용자에게 사실처럼 보인다.
- 좌표는 좌표계를 모르므로 이번에는 **저장만 하고 지도에 쓰지 않는다.** 저장해두면 나중에 좌표계가 확인됐을 때 재수집 없이 쓸 수 있다.
- 각 필드에 "코드표 미확인" 주석을 남긴다.

### D5. 프롬프트 v2와 재분석 비용

`renderItemPrompt`가 `AuctionItem`을 통째로 직렬화하므로 필드 추가만으로 입력이 늘어난다. 그래도 프롬프트 본문을 고쳐야 한다:

- 새 정보로 가능해진 판단을 지시한다: **면적당 가격**(최저가 ÷ 면적), **차수별 저감 추이**, **일괄매각 여부**의 의미.
- **권리관계·임차인 정보가 이 소스에 존재하지 않는다는 사실**을 프롬프트에 명시한다. 지금 프롬프트는 "주어지지 않았다"고만 하는데, "이 소스로는 얻을 수 없다"가 더 정확하고, 모델이 없는 정보를 추론하려 드는 것을 막는다.
- `PROMPT_VERSION`을 `v2`로 올린다. 이는 **분석된 모든 물건을 재분석 대상으로 만든다** — 의도된 비용이며, `maxReanalysisPerRun`(2)과 `reanalysisCooldownHours`(24)가 속도를 제한한다. README에 이미 이 경고가 있다.

### D6. 어댑터 스키마 확장 시 실패 처리 유지

`schema.ts`의 행 스키마는 **행 내부 필드를 전부 optional**로 두는 기존 방침을 유지한다. 새 필드를 required로 만들면 소스가 하나만 안 보내도 회차 전체가 `ResponseSchemaError`로 죽는다 — 부가 정보 때문에 수집이 멈추는 것은 잘못된 트레이드오프다.

- 대신 "행은 왔는데 확장 필드가 전부 비었다" 같은 경우는 필드명 변경 의심 경고를 로그로 남긴다(기존에 자연키 누락 행에 대해 같은 패턴을 쓰고 있다).

## Risks / Trade-offs

- [프롬프트 v2로 전체 재분석이 유발됨] → 의도된 비용. 한도·쿨다운이 속도를 제한하고, `/status`의 회차 기록으로 진행을 관측할 수 있다(3회차 산출물). 다만 물건 수백 건 × 분석 1회이므로 실제 비용을 미리 가늠해 README에 적는다.
- [확장 필드가 소스 변경으로 사라져도 조용히 NULL이 됨] → D6의 경고 로그로 감지한다. 다만 개별 필드 단위 감지는 하지 않는다 — 부가 필드마다 알람을 걸면 소음이 된다.
- [좌표·코드값을 저장하지만 쓰지 못함] → 저장 비용은 무시할 수준이고, 나중에 의미가 확인됐을 때 재수집이 필요 없다는 이득이 크다.
- [`items` 테이블 컬럼이 많아짐] → 스칼라 값이고 조회 패턴이 단순해 문제되지 않는다. 컬럼이 40개를 넘어가면 그때 분리를 검토한다.

## Open Questions

- 차수별 최저가를 감시 대상에 넣을지 — 실데이터에서 1차 최저가와 어떻게 다르게 움직이는지 본 뒤 결정한다.
- 면적당 가격을 목록의 정렬 기준으로 노출할지 — 분석 결과를 몇 번 본 뒤 판단해도 스펙·구조에 영향 없다.
