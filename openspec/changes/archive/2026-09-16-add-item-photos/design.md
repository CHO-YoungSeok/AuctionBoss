# Design: add-item-photos

## Context

동기는 proposal.md 참조. 이 change가 위험한 이유는 하나다 — **유일하게 새로운 종류의 외부 요청을 추가**하고, 차단은 IP 단위라 실패하면 사진뿐 아니라 물건 수집 전체가 멈춘다.

실측 근거(`NOTES.md`):
- §6.1: 차단 임계 5분에 15회 미만. 차단은 HTTP 200 유지, 13분 이상 지속, IP 단위
- §12: 수집 회차는 13요청 / 57초 / 10분 간격. 이 밀도는 안전이 실측됨
- §10.2: 사진이 `csPicLst[i].picFile`에 base64 PNG로 들어옴 — **DERIVED**(실물 미확인)
- §10.5: 물건당 1요청, 389건이면 402요청 = 임계의 27배

## Goals / Non-Goals

**Goals:**
- 사진을 보여주되 **수집을 멈추지 않기**
- 상세 엔드포인트 명세를 DERIVED에서 CONFIRMED로 올리기
- 이미 가져온 사진을 다시 요청하지 않기

**Non-Goals:**
- 전량 사진 수집(불가능), 갤러리 UI, 감정평가서·현황조사서, 사진 기반 분석

## Decisions

### D1. 상세 페이지 렌더 경로에서 fetch하지 않는다

가장 자연스러워 보이는 설계("사용자가 상세를 열면 그때 가져온다")를 **채택하지 않는다.**

- `/items/[id]`는 `force-dynamic` 서버 컴포넌트다. 여기서 외부 fetch를 하면 (a) 페이지 응답이 외부 사이트 지연에 묶이고, (b) 차단 시 상세 페이지가 통째로 실패하거나 수 초 멈추고, (c) **봇·프리페치·새로고침이 그대로 요청 수가 된다.**
- 결정적으로 Next.js `<Link>`가 목록에서 상세를 **프리페치**한다. 사용자가 클릭하지 않은 물건도 요청될 수 있고, 목록에서 20건을 빠르게 열어보는 것이 정확히 "5분에 20요청"이라 임계를 넘는다.
- 앞서 내가 "사람의 클릭 속도가 자연스러운 레이트리밋"이라고 판단한 적이 있는데 **틀렸다.** 프리페치를 계산에 넣지 않았다.

### D2. 저속 큐 워커 — 수집과 완전히 분리

별도 워커가 사진 없는 물건을 하나씩 골라 **물건당 수십 초 간격**으로 가져온다.

- 간격의 근거: 수집 회차가 13요청/57초로 안전하다는 실측이 있다. 사진 워커가 30초 간격이면 5분에 10요청이고, 수집기가 같은 5분 안에 13요청을 보낼 수 있으므로 최악의 경우 합계 23요청이 된다 — **이건 임계를 넘는다.**
- 따라서 **두 워커의 요청을 합쳐서 예산을 잡아야 한다.** 사진 워커 간격을 60초 이상으로 두고, 수집 회차가 도는 동안에는 사진 요청을 멈추는 것이 안전하다. 정확한 값은 구현 시 산수를 다시 하고 설정으로 노출한다.
- 이미 가져온 물건은 재요청하지 않는다. 실패한 물건도 즉시 재시도하지 않는다(영구 실패 물건이 큐를 막으면 안 된다).

### D3. 차단 백오프를 워커 간 공유한다

사진 워커가 차단을 유발하면 수집기도 막힌다. 같은 IP이기 때문이다.

- `collector_state`(6회차에서 만든 키-값 테이블)에 공유 백오프 종료 시각을 둔다. 어느 워커든 차단을 만나면 그 값을 쓰고, **두 워커 모두 그 시각까지 요청하지 않는다.**
- 이게 없으면 사진 워커가 차단을 만든 뒤에도 수집기가 계속 요청해 차단이 연장된다.
- `WORKER_KINDS`를 셋으로 늘려 `/status`에서 사진 워커도 보이게 한다. 지금 2개 고정이고 테스트가 그걸 고정하고 있으므로 함께 갱신한다.

### D4. 사진 저장은 파일시스템, DB에는 경로만

base64 이미지를 DB에 넣으면 물건당 2MB 이상 × 389건이다. 현재 DB가 1.2MB인 것과 자릿수가 다르다.

- 파일로 저장하고 DB에는 경로·크기·수집 시각만 둔다. `data/photos/<itemId>/<n>.gif` 또는 매직 바이트 기반 확장자.
- **`.gitignore`에 `/data/`를 반드시 추가한다.** (추가 완료) 수백 MB가 저장소에 들어가면 안 된다.
- **포맷 실측 발견사항 (Stage B 실측, 2026-09-11)**:
  - 소스 XML의 `setSrc("data:image/png...")`와 달리, 실제 base64 바이너리는 매직 바이트 `GIF89a`를 가진 **GIF 포맷**이다 (파일명 `picTitlNm`이 `.jpg`여도 실제 바이너리는 GIF89a).
  - 따라서 파일 저장 시 확장자를 `.gif`로 저장하거나, `detectImageExtension` 같은 매직 바이트 판별 함수를 기반으로 확장자를 결정한다.
- **용량 실측 발견사항 (Stage B 실측, 2026-09-11)**:
  - 실측 케이스(2026타경101037)에서 15장 반환, 장당 100~200KB (평균 약 136KB).
  - 물건당 15장 × 약 150KB ≈ **2.2MB** (base64 JSON 상 약 2.7MB).
  - 389건 전량 수집 시 약 **850MB** 수준.
- 물건이 삭제되는 경로는 현재 없지만, 있다면 파일도 함께 지워야 한다는 점을 코드에 남긴다.

### D5. B단계를 건너뛰지 않는다

상세 엔드포인트는 **한 번도 호출된 적이 없다.** 명세는 화면 정의 XML에서 읽은 것이고, base64라는 것도 코드 문자열 조합에서 유추한 DERIVED다.

- C단계 워커를 만들기 전에 **단 1건**을 호출해 실제 응답을 확인한다. 응답이 예상과 다르면 워커 설계가 통째로 바뀐다.
- 그 1회 요청조차 차단 위험을 진다. 수집 회차와 시간을 벌려서 보낸다.
- 받은 응답을 fixture로 남겨 이후 테스트가 네트워크 없이 돌게 한다.
- **진행 상황 (2026-09-11)**: Stage B 단 1회 프로브 성공 (2026타경101037), 상세 zod 스키마 정의 및 경량 실측 fixture/단위테스트 작성 완료.

### D6. 사진이 없어도 화면이 정상이어야 한다

389건 대부분은 오랫동안 사진이 없을 것이다(물건당 1요청 × 60초 간격 = 하루 최대 1,440건이지만 실제로는 훨씬 적게 돈다).

- 사진 없음이 기본 상태다. "사진 없음"이 오류처럼 보이면 안 되고, 아직 안 가져온 것인지 원래 없는 것인지 구별할 수 있으면 더 좋다.
- 사진 수집을 시도했으나 실패한 물건도 구별한다 — 영원히 "대기 중"으로 보이면 안 된다.

## Risks / Trade-offs

- [사진 워커가 차단을 유발해 수집이 멈춤] → D3의 공유 백오프. 그래도 가장 큰 위험이므로 워커 간격을 보수적으로 잡고 실측하며 조정한다.
- [상세 응답이 예상과 다름] → D5의 B단계가 그걸 확인하는 단계다. 다르면 C단계 설계를 다시 한다.
- [사진 저장 용량] → 파일시스템 + gitignore. 장당 약 136KB, 15장 기준 물건당 ~2.2MB, 전량 389건 기준 ~850MB 수준으로 실측 확인됨.
- [큐가 영원히 안 끝남] → 389건 × 60초 = 6.5시간. 사용자가 보는 물건부터 가져오는 우선순위(관심 물건 우선)를 검토하되, 구현 복잡도를 보고 판단한다.

## Open Questions

- 사진 워커와 수집기의 합산 요청 예산 — 산수는 D2에 있지만 실제 안전값은 며칠 관측이 필요하다.
- 물건당 사진 장수 분포 — Stage B 실측(2026타경101037)에서 15장(총 2.04MB 바이너리, GIF89a 포맷) 확인 완료.
