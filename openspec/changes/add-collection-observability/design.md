# Design: add-collection-observability

## Context

동기는 proposal.md 참조. 활용할 수 있는 기존 자산:

- 어댑터가 실패를 **이미 구분된 오류 타입**으로 던진다: `SourceBlockedError`(상위) → `RobotDetectedError` / `WafBlockedError`, 그리고 `ResponseSchemaError`, `SourceRequestError`. 차단 구별에 새 판정 로직이 필요 없다 — 타입 이름을 기록하면 된다.
- `workers/collector.ts`가 회차 시작·완료·차단 백오프·중첩 건너뜀 지점에서 이미 로그를 찍는다. 기록 지점을 새로 찾을 필요가 없고 그 자리에 기록 호출을 넣으면 된다.
- `upsertItems`가 `{inserted, updated, changed}`를 반환하고 collector가 이미 그 셋을 받아 로그에 찍는다(직전 change에서 `changed`를 추가했다).
- 분석 워커는 **DB를 직접 쓰지 않고 HTTP로만 통신한다**(기존 D5 결정). 이 제약이 아래 D3을 강제한다.

## Goals / Non-Goals

**Goals:**
- 워커가 죽었는지, 차단됐는지, 정상인지를 웹에서 확인
- 차단을 일반 실패와 구별해 기록
- 기록이 워커를 방해하지 않음
- 기록이 무한히 자라지 않음

**Non-Goals:**
- 알림, 차트, 자동 대응(주기 자동 조절), 인증
- 물건 데이터의 품질 판정(가짜 변경 필터링) — 이번 범위는 *관측*이고 판정 규칙은 데이터를 며칠 본 뒤의 별도 change다

## Decisions

### D1. 단일 `worker_runs` 테이블, 워커 종류를 컬럼으로

`worker_runs(id, worker, started_at, finished_at, outcome, error_kind, error_message, detail, created_at)`

- `worker`: `'collector' | 'analyzer'`. 테이블을 둘로 나누지 않는 이유: 상태 화면이 두 워커를 나란히 보여주고, 조회·집계·보관 정리 로직이 완전히 동일하다. 나누면 같은 코드를 두 번 쓴다.
- `outcome`: `'running' | 'success' | 'failed' | 'blocked' | 'skipped'`. **`blocked`를 `failed`의 하위가 아니라 별도 값으로 둔다** — 스펙이 구별을 MUST로 요구하고, 화면에서 다른 취급을 받고, 집계에서 따로 세어야 한다.
- `detail`: 워커별로 다른 수치를 담는 JSON 텍스트(collector: 대상 법원, 페이지 수, 물건 수, `inserted`/`updated`/`changed`; analyzer: 신규·재분석·성공·실패 건수). 왜 정규화된 컬럼이 아닌가: 두 워커의 수치 집합이 다르고 앞으로 더 늘어난다. 컬럼으로 두면 워커를 추가할 때마다 스키마가 바뀌고 한쪽은 항상 NULL이다. **단, 집계에 쓰이는 값은 예외** — `changed` 누적 집계가 스펙 요구사항이라 JSON 안에 있으면 SQL로 합산할 수 없다. `items_changed` 같은 집계용 컬럼을 따로 둔다(nullable). 즉 **JSON은 표시용, 컬럼은 집계용**이고 이 이중화는 의도적이다.
- `error_kind`는 오류 클래스 이름(`RobotDetectedError` 등)을 그대로 넣는다. 새 오류 타입이 생겨도 스키마가 안 바뀐다.
- `skipped` 회차의 사유(`overlap` / `backoff`)는 `error_kind`에 넣는다. 별 컬럼을 만들 만한 정보량이 아니다.

### D2. 회차 기록은 시작 시 행을 만들고 종료 시 갱신

`startRun(worker) -> runId` → `finishRun(runId, outcome, ...)`.

- 왜 종료 시 한 번에 쓰지 않는가: 스펙이 "진행 중 회차"를 조회 가능하게 요구한다. 더 중요하게는, **워커가 회차 도중에 죽으면 종료 기록이 영원히 안 남는다** — 종료 시 한 번만 쓰면 그 회차는 존재조차 하지 않아 "워커가 죽었다"는 사실이 오히려 감춰진다. 시작 행이 있으면 `running`인데 오래된 회차가 남아 이상 상태를 드러낸다.
- `skipped`는 시작·종료가 같은 순간이므로 한 번에 쓴다.

### D3. 분석 워커의 기록은 API 경유 (`POST /api/worker-runs`, `PATCH`/`POST /api/worker-runs/[id]`)

기존 D5 결정(분석 워커는 HTTP로만 통신)을 깨지 않는다. 수집 워커는 이미 DB를 직접 쓰므로 저장소 함수를 직접 호출한다.

- 즉 **같은 기록이 두 경로로 들어온다**(collector: 저장소 직접, analyzer: HTTP). 저장소 함수 하나를 두고 API가 그걸 호출하는 얇은 층이 되게 해서 로직 중복을 막는다.
- 이 API는 쓰기 엔드포인트인데 인증이 없다. 현 단계가 개인/내부용 로컬 실행이라는 전제이며(README에 이미 명시), 인증은 보류 항목이다. **다만 이 엔드포인트가 외부에 노출되면 임의 기록을 주입할 수 있다는 점을 README에 적는다** — 조용히 넘기면 나중에 배포할 때 사고가 된다.

### D4. 기록 실패가 워커를 죽이지 않음

기록 호출은 전부 try/catch로 감싸 실패를 로그로만 남긴다. 스펙의 MUST NOT 요구다.

- 이게 필요한 이유가 구체적이다: 기록은 부가 기능인데, 기록 테이블 문제로 수집이 멈추면 부가 기능이 본체를 죽이는 것이다. 특히 D2 때문에 회차마다 쓰기가 2번 일어나므로 실패 가능성도 2배다.
- **주의**: `finishRun` 실패를 삼키면 그 회차는 영원히 `running`으로 남는다. 상태 판정(D5)이 오래된 `running`을 정상으로 보지 않아야 한다.

### D5. 상태 판정: 기록에서 도출, 저장하지 않음

`getWorkerStatus(worker) -> { state, lastSuccessAt, lastRun }`. `state`는 `'ok' | 'blocked' | 'failed' | 'stale'`.

판정 순서(먼저 맞는 것을 채택):
1. 기록이 없음 → `stale`
2. 마지막 성공(또는 마지막 기록)이 기대 주기 × N보다 오래됨 → `stale` (N은 상수, 기본 3). **오래된 `running` 회차도 여기 걸린다.**
3. 가장 최근의 완료된 회차가 `blocked` → `blocked`
4. 가장 최근의 완료된 회차가 `failed` → `failed`
5. 그 외 → `ok`

- 왜 상태를 저장하지 않는가: 저장하면 워커가 죽을 때 마지막 상태(`ok`)가 그대로 굳어 정확히 알고 싶은 순간에 거짓말을 한다. 기록에서 매번 도출하면 "시간이 지났다"는 사실 자체가 상태를 바꾼다.
- 기대 주기는 설정(`intervalMs`)에서 읽는다. 하드코딩하면 주기를 바꿀 때 판정이 틀어진다.
- `skipped`는 상태 판정에서 **최근 회차로 취급하지 않는다**(3·4번에서 제외). 중첩 건너뜀은 정상 동작이고, 백오프 건너뜀은 그 앞의 `blocked`가 이미 상태를 결정한다.

### D6. 보관 상한: 건수 기준, 기록 시 정리

워커별 최대 보존 건수를 설정으로 둔다(기본 1000 — 10분 주기면 약 7일). 새 회차를 기록할 때 초과분을 삭제한다.

- 왜 건수인가: 기간 기준은 주기를 바꾸면 행 수가 달라져 상한의 의미가 흔들린다. 건수는 상한이 곧 최대 행 수다.
- 왜 별도 정리 작업이 아닌가: 정리 전용 스케줄러를 하나 더 만들 만한 일이 아니고, 그것도 죽을 수 있다. 쓰기 시점에 정리하면 기록이 도는 동안은 정리도 반드시 돈다.
- 매 회차 `DELETE`가 비용이라 정리를 **가끔만** 실행할 유혹이 있는데, 하루 144행 규모에서는 매번 해도 무해하다. 조건 분기를 넣는 쪽이 더 비싸다.

### D7. 상태 화면은 `/status` 서버 컴포넌트

기존 페이지들과 같은 방식(저장소 직접 호출, `force-dynamic`). 차단 상태는 색과 문구로 눈에 띄게 구별한다. 목록·상세 페이지에서 상태 페이지로 가는 링크를 둔다 — 접근 경로가 없으면 만들어도 아무도 안 본다.

## Risks / Trade-offs

- [`detail` JSON과 집계용 컬럼의 이중화가 어긋날 수 있음] → 기록 함수 한 곳에서만 둘을 쓰게 하고, 그 함수의 테스트로 두 값이 일치하는 것을 고정한다.
- [쓰기 API에 인증이 없음] → 현 단계는 로컬 전용. README에 노출 시 위험을 명시하고, 인증 도입 시 이 엔드포인트를 포함할 항목으로 남긴다.
- [기록이 늘면서 상태 페이지 조회가 느려짐] → 보관 상한이 1000건이라 무해하다. 인덱스는 `(worker, started_at DESC)`.
- [워커가 회차 중간에 죽어 `running`이 남음] → D5의 2번 판정이 이를 `stale`로 잡는다. 다만 그 고아 행은 계속 남는데, 보관 상한이 결국 지운다. 굳이 기동 시 고아 정리를 넣지 않는다(워커가 여러 개면 남의 회차를 지울 수 있다).
- [수집 실패를 관측하게 됐지만 자동 대응은 없음] → 이번 범위는 관측까지다. 사람이 보고 판단한다.

## Open Questions

- `stale` 판정의 배수 3이 적절한지 — 수집이 40페이지를 도는 데 걸리는 시간이 주기에 근접하면 오판이 날 수 있다. 실제 회차 소요 시간이 기록되기 시작하면 근거를 갖고 정할 수 있다(그게 이 change의 산출물이다).
- 집계 기간(예: 최근 24시간)을 고정할지 파라미터로 열지 — 화면을 써보고 정해도 스펙·구조에 영향 없다.
