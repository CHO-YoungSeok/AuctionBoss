## MODIFIED Requirements

### Requirement: 소스 어댑터 계약
모든 소스 접근은 `AuctionSource` 어댑터 인터페이스를 통해야 하며(MUST), 어댑터는 소스 고유 형식을 정규화된 물건 모델로 변환해 반환해야 한다(SHALL). 정규화 모델은 최소한 다음을 포함해야 한다(SHALL):

- **식별·기본**: 사건번호, 물건번호, 법원, 소재지, 용도, 감정가, 최저매각가격, 매각기일, 유찰횟수, 진행상태
- **면적**: 최소·최대 면적과 건물 구조·면적 서술
- **차수별 최저매각가격**: 회차별 최저가와 최저가율
- **용도 분류 코드**: 대·중·소분류
- **소재지 구조화 값**: 시/도, 시/군/구, 동, 대표지번, 건물명
- **좌표**: x·y 좌표와 좌표 수준
- **매각 관련**: 매각기일 시각, 매각장소, 매각결정기일, 매각기일 회차
- **사건 관련**: 비고, 중복·병합 사건번호, 담당계와 연락처

수집기·저장소·화면은 소스 고유 필드명이나 형식에 의존해서는 안 된다(MUST NOT).

소스가 값을 주지 않는 필드는 **없음(null)으로 표현해야 하며**(SHALL), 0이나 빈 문자열 같은 대체값으로 채워서는 안 된다(MUST NOT) — 값이 0인 것과 값이 없는 것은 다른 사실이다.

의미를 확정하지 못한 소스 코드값(진행상태 코드 등)은 **원문 그대로 보존해야 하며**(SHALL), 어댑터가 임의로 해석한 값으로 대체해서는 안 된다(MUST NOT). 반대로 소스에 대응 필드가 없어 파생한 값은 파생값임을 코드에 명시해야 한다(SHALL).

새 필드가 추가되어도 기존 필드의 의미와 기존 소비자의 동작은 바뀌어서는 안 된다(MUST NOT).

정규화 모델은 소스의 상세 조회에 필요한 식별자도 보존해야 한다(SHALL). 화면 표시용 사건번호와 소스 내부 식별자가 다를 수 있으므로 같은 값으로 가정해서는 안 된다(MUST NOT).

#### Scenario: 어댑터 교체
- **WHEN** 법원경매정보 스크래핑 어댑터를 다른 소스 어댑터로 교체하면
- **THEN** 어댑터 구현 외의 수집기·저장소·화면 코드는 변경 없이 동작한다

#### Scenario: 정규화된 결과 반환
- **WHEN** 어댑터가 소스에서 물건 목록을 조회하면
- **THEN** 정규화 모델 배열이 반환되고, 필수 필드(사건번호, 물건번호, 법원)가 누락된 항목은 결과에 포함되지 않고 경고 로그로 남는다

#### Scenario: 확장 필드 보존
- **WHEN** 소스 응답에 면적·차수별 최저가·용도 분류 코드·좌표가 들어 있으면
- **THEN** 그 값들이 정규화 모델에 담겨 저장되고, 화면과 분석 입력에서 사용할 수 있다

#### Scenario: 값이 없는 확장 필드
- **WHEN** 소스 응답에서 일부 확장 필드가 비어 있거나 누락되면
- **THEN** 해당 필드는 없음으로 저장되고, 물건 자체는 정상 수집되며 기존 필드의 처리에 영향을 주지 않는다

#### Scenario: 의미를 모르는 코드값
- **WHEN** 소스가 코드표를 알 수 없는 상태 코드를 보내면
- **THEN** 그 값이 원문 그대로 보존되고, 어댑터가 임의로 해석한 값으로 바뀌지 않는다
#### Scenario: 상세 조회 식별자 보존
- **WHEN** 어댑터가 물건을 정규화하면
- **THEN** 소스의 상세 조회에 필요한 식별자가 함께 보존된다
