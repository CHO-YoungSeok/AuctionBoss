# Design: ux-overhaul-phase2

## Context

동기는 proposal.md 참조. 이 Phase는 **목록 쿼리 계약을 건드리는 유일한 사이클**이고, 그래서 지금까지 중 회귀 위험이 가장 크다.

필터 파라미터 하나를 추가하려면 여섯 곳을 동시에 고쳐야 한다:

| # | 위치 | 빠뜨리면 |
|---|---|---|
| 1 | `ITEM_QUERY_PARAMS` | 파서가 **조용히 무시**한다(오류 아님). 폼은 보내는데 아무 일도 안 일어난다 |
| 2 | zod 스키마(strict/lenient 양쪽) | 검증이 안 되거나 400이 안 난다 |
| 3 | `ItemQuery` 타입 + 변환 | 타입은 잡아주지만 누락 자체는 못 잡는다 |
| 4 | **`hasActiveFilters`** | **필터로 0건일 때 "DB가 비었다"는 거짓 안내가 뜨고 초기화 링크가 없어 빠져나갈 수 없다.** 실제로 `analyzed`가 이렇게 빠져 사고가 났다 |
| 5 | `buildFilter` | 필터가 실제로 안 걸린다. 그리고 `where`가 `total` 카운트에도 쓰이므로 여기 조건 하나가 페이지 수까지 바꾼다 |
| 6 | `itemQuerySearchParams` | **페이지 "다음"을 누르면 필터가 사라진다** |

## Goals / Non-Goals

**Goals:**
- 사용자가 실제로 후보를 좁힐 수 있게
- 기존 계약을 깨는 항목을 하나로 격리하고 명시적으로 처리
- 여섯 곳 동시 수정 절차를 한 번 확립해 나머지가 따라가게

**Non-Goals:**
- 사진, 관련 물건, 지도, 관심 화면 통일
- 기본 정렬·기본 결과 집합 변경

## Decisions

### D1. 순서: 순수 추가 → 계약 변경 → 정렬

**지역 필터를 가장 먼저** 한다. 순수 추가라 기존 조건과 상호작용이 없고, 위 여섯 곳을 고치는 절차를 한 번 확립해두면 나머지가 그 패턴을 따라간다.

순서: `지역` → `가격 폼` → `기일 범위` → `관심 필터` → **`용도 토큰`(계약 파괴)** → `면적당 가격 정렬`

- 용도를 뒤로 미루는 이유: 유일하게 **기존 동작을 바꾸는** 항목이다. 순수 추가 항목들이 먼저 안정된 뒤에 손대야 무엇이 깨졌는지 구별할 수 있다.
- 면적당 가격 정렬은 **Phase 1의 면적 정직화가 선행돼야 한다.** 안 그러면 "저평가 순 정렬"이 실제로는 대지면적 큰 순 정렬이 된다.

### D2. 용도 토큰 매칭 — 계약 변경을 숨기지 않는다

`"오피스텔"` 체크 시 지금 24건, 바꾸면 139건이다.

- 선택지는 저장된 복합 문자열을 쉼표로 쪼개 중복 제거해 만든다. `listUsageTypes`를 확장한다.
- 매칭은 `IN`이 아니라 토큰 비교다. SQLite에서 문자열을 쪼개는 대신, **저장 시점에 쪼개진 형태를 별도로 갖는 방법**과 **조회 시 `LIKE` 패턴으로 토큰 경계를 맞추는 방법**이 있다. 후자는 `,오피스텔,` 형태로 앞뒤에 구분자를 붙여 비교하면 부분 문자열 오탐(`"오피스텔형"`)을 피할 수 있다. 데이터 규모가 수백 건이라 후자로 충분하다.
- **README의 "저장된 값과 정확히 일치" 서술을 함께 고친다.** 문서가 코드와 어긋나면 없는 것보다 해롭다.
- 기존 필터 테스트를 갱신하되, **갱신한 테스트가 새 동작을 실제로 고정하는지** 확인한다(수정을 되돌려 실패를 보는 방식).

### D3. 가격 폼은 표시만 바꾸고 API는 그대로

입력을 억/만원으로 받되 **제출되는 파라미터는 원 정수 그대로**다.

- 왜: `minPrice`/`maxPrice`는 이미 스펙과 테스트로 고정돼 있고, 잘못된 값에 400을 내는 동작도 테스트가 있다. 표시 단위 때문에 그걸 흔들 이유가 없다.
- 폼이 억/만원을 원으로 변환해 hidden field로 보내는 방식은 클라이언트 JS가 필요하다. **JS 없이 하려면 서버가 변환**해야 하므로, 억/만원 전용 파라미터(예: `minEok`)를 추가로 받아 서버에서 원으로 환산하고 기존 파라미터와 함께 쓰는 방식이 맞다. 둘 다 오면 우선순위를 정해 문서화한다.
- 프리셋은 단순 링크다 — 이미 계산된 원 단위 값이 들어간 URL.

### D4. 기일 범위와 관심 필터는 반드시 opt-in

- "지난 기일 제외"를 기본값으로 하면 오늘 기준 121건(31%)이 사라진다. 기본 `total`을 전제한 테스트가 대량으로 깨지고, 사용자는 "물건이 갑자기 줄었다"로 읽는다. 6회차에서 법원을 중간에 끊지 않기로 한 것과 같은 이유다.
- 관심 필터는 `BOOKMARKED_EXPR`이 이미 있지만 그건 **`WHERE`에 관여하지 않는 스칼라 서브쿼리**로 설계됐고 주석이 그걸 명시한다. 그 안전 보장을 없애지 말고 **별도 `EXISTS` 조건을 추가**한다.

### D5. 필터 상태 가시화는 쿼리를 건드리지 않는다

칩·접기·페이지 크기는 전부 기존 `ItemQuery`에서 파생된다. 쿼리 계약 무변경이므로 **다른 항목과 병렬로 진행할 수 있다.**

- 칩의 해제 링크는 `itemListHref(query, {해당 필드: undefined})`로 만든다. 새 함수를 만들지 않는다.
- 폼 접기는 `<details>`다. 상세의 "이전 분석"에서 이미 쓰는 JS 없는 선례가 있다.

## Risks / Trade-offs

- [여섯 곳 중 하나를 빠뜨림] → 필터를 추가할 때마다 여섯 곳을 체크리스트로 확인하고, 특히 `hasActiveFilters` 누락은 "필터 걸고 0건일 때 올바른 안내가 뜨는가" 테스트로 잡는다. 이건 필터마다 반복한다.
- [용도 계약 변경이 다른 것을 깨뜨림] → 워커는 `usage`를 쓰지 않으므로 안전하다. 목록 UI와 API 테스트만 영향을 받는다.
- [필터가 늘어 조합 폭발] → 조합 테스트를 전수로 하지 않고, 각 필터 단독 + 전체 조합 + `total` 일치를 확인한다.
- [정렬 추가 시 NULL 처리] → `bidRatio`가 이미 확립한 관례(`(expr) IS NULL`을 선행 키로)를 따른다. 면적 없는 물건이 방향과 무관하게 뒤로 가야 한다.

## Open Questions

- 억/만원 입력과 원 단위 파라미터가 동시에 오면 어느 쪽이 이기는가 — 구현 시 정하고 문서화한다.
- `dong` 필터가 필요해지는 시점 — 지역을 좁힌 뒤에도 결과가 많으면 그때 검토한다.
