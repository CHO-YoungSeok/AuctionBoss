# Design: scale-collection-scheduling

## Context

동기는 proposal.md 참조. 확정된 사실:

- 실측 차단 임계: **5분에 15회 미만**(`NOTES.md` §6.1). 차단은 13분 이상 지속되고 IP 단위다.
- 현재 회차당 요청 = 쿠키 1 + 페이지 N. 서울중앙 2개월 = 12페이지 → 13요청.
- `CollectScope`는 이미 법원 배열이고, 어댑터의 `fetchActiveItems(scope)`가 배열을 순회하며 `pagesRequested`를 합산해 반환한다(3회차).
- 3회차의 `worker_runs`에 실제 요청 페이지 수가 기록된다 — **차단으로 중단된 회차도 그때까지 보낸 수가 남는다.** 예산을 추측이 아니라 실측으로 정할 수 있게 됐다.
- `CollectorRunDetail`에 `targetCourts: string[]`가 이미 있다.

## Goals / Non-Goals

**Goals:**
- 법원 수가 늘어도 회차당 요청 수가 상한 아래로 유지
- 모든 법원이 공평하게 순환(특정 법원이 영구히 밀리지 않음)
- 워커를 재시작해도 로테이션이 이어짐
- 법원 1곳 설정에서 기존과 완전히 동일한 동작

**Non-Goals:**
- 상용 API 어댑터, 법원별 다른 주기, 변동 빈도 기반 적응형 스케줄링
- 실제 60개 법원 활성화 — 이 change는 그것이 **가능해지는 구조**만 만든다

## Decisions

### D1. 예산의 단위는 "요청 수"가 아니라 "법원 수"

회차당 처리할 **법원 수 상한**(`maxCourtsPerRun`, 기본 1)을 둔다.

- 왜 요청 수가 아닌가: 한 법원의 페이지 수는 그 법원의 물건 수에 따라 달라져 **요청을 보내보기 전에는 모른다.** 요청 수로 예산을 잡으면 "3페이지 남았는데 예산이 1 남음" 같은 상태에서 회차를 중간에 끊게 되고, 그러면 그 법원은 일부만 수집된 채로 남는다. 부분 수집된 법원은 "이 법원의 물건이 줄었다"로 오해될 수 있어 더 나쁘다.
- 법원 단위로 끊으면 **각 법원은 항상 완전히 수집되거나 아예 건너뛰어진다.** 데이터의 의미가 흐려지지 않는다.
- 페이지 상한(`maxPages`)은 이미 있으므로 한 법원의 최대 요청 수는 이미 유계다. 법원 수 × 페이지 상한이 회차 최대 요청이 된다 — 설정에서 계산 가능하다.
- 안전장치로 회차 요청 수 상한도 함께 두되(`maxRequestsPerRun`), 이건 **초과 시 다음 법원을 시작하지 않는** 용도다. 진행 중인 법원을 중간에 끊지 않는다.

### D2. 로테이션 위치는 `worker_runs`에서 도출하지 않고 별도로 저장

작은 키-값 테이블(`collector_state(key PK, value, updated_at)`)에 다음 시작 법원 코드를 저장한다.

- 왜 `worker_runs`의 마지막 `targetCourts`에서 계산하지 않는가: 그건 관측 기록이고, 보관 상한(기본 1000행)에 걸려 지워질 수 있다. **운영 상태를 관측 로그에서 재구성하는 건 취약하다** — 로그를 지우면 상태가 사라진다.
- 왜 파일이 아닌 DB인가: 이미 DB가 있고 트랜잭션이 있다. 파일을 쓰면 워커 재시작·동시 실행 시 정합성을 따로 챙겨야 한다.
- 키-값 테이블로 만드는 이유: 로테이션 위치 하나 때문에 전용 테이블을 만들기엔 과하고, 앞으로 비슷한 소규모 운영 상태(예: 마지막 성공 법원별 시각)가 더 생길 수 있다.
- 저장하는 값은 **인덱스가 아니라 법원 코드**다. 설정에서 법원 목록의 순서가 바뀌거나 중간에 하나가 삭제되면 인덱스는 엉뚱한 법원을 가리킨다. 코드를 저장하고 목록에서 그 위치를 찾되, 없으면 처음부터 시작한다.

### D3. 순환은 목록 순서대로, 한 바퀴 개념을 유지

법원 목록을 원형으로 보고 저장된 위치부터 `maxCourtsPerRun`개를 처리한 뒤 다음 위치를 저장한다.

- 목록 순서를 쓰는 이유: 예측 가능하다. "가장 오래 수집 안 된 법원 우선" 같은 규칙은 더 똑똑해 보이지만, 수집 실패가 반복되는 법원이 매번 선택돼 다른 법원을 굶길 수 있다.
- **한 바퀴 소요 시간** = `ceil(법원 수 / maxCourtsPerRun) × intervalMs`. 이 값을 계산해 상태 화면에 보여준다. 법원을 추가하면 이 숫자가 즉시 나빠지는 것을 눈으로 보게 하는 것이 목적이다 — 신선도의 대가를 모르고 법원을 늘리는 것을 막는다.
- 회차 기록의 `targetCourts`에 이번 회차가 실제로 돈 법원을 남긴다(필드는 이미 있다).

### D4. 차단 백오프는 로테이션 전체에 적용

한 법원에서 차단되면 **그 회차를 중단하고 로테이션 위치를 전진시키지 않는다.** 백오프가 끝나면 같은 법원부터 다시 시작한다.

- 왜 위치를 전진시키지 않는가: 전진시키면 차단당한 법원이 한 바퀴 뒤로 밀려 그 법원만 계속 수집이 늦어진다.
- 왜 다른 법원으로 넘어가지 않는가: 차단은 **IP 단위**다(실측). 법원을 바꿔도 같은 IP이므로 계속 막히고, 요청만 더 보내 차단이 길어진다. 기존 백오프 로직(3회차에서 `skipped/backoff`로 기록)을 그대로 쓴다.

### D5. 법원 1곳에서는 기존과 완전히 동일

`maxCourtsPerRun` 기본값 1 + 법원 1곳이면 매 회차 그 법원을 돈다 — 지금과 같다. 로테이션 위치는 항상 같은 곳을 가리킨다.

- 이건 **회귀 테스트로 고정한다.** 기존 설정 파일이 그대로 유효해야 하고, 수집 결과·요청 수·기록이 지금과 달라지면 회귀다.
- 새 설정 필드는 기본값을 가지되, 이 프로젝트의 기존 방침(설정이 잘못되면 조용히 기본값으로 넘어가지 않고 실패)을 따라 zod로 검증한다.

## Risks / Trade-offs

- [법원을 늘리면 신선도가 나빠짐] → 피할 수 없는 트레이드오프다. 한 바퀴 소요 시간을 화면에 표시해 대가를 명시적으로 만든다. 숨기지 않는 것이 최선의 대응이다.
- [로테이션 상태가 꼬여 특정 법원이 계속 건너뛰어짐] → 저장값을 코드로 두고 못 찾으면 처음부터 시작하게 해 자가 복구된다. 회차 기록의 `targetCourts`로 실제 순환을 관측할 수 있다.
- [법원 수 × 페이지 상한이 여전히 임계를 넘을 수 있음] → `maxRequestsPerRun` 안전장치. 다만 실제 안전 예산은 아직 실측되지 않았다 — 3회차의 기록이 며칠 쌓여야 안다. 기본값은 현재 검증된 수준(법원 1곳 = 13요청)을 넘지 않게 잡는다.
- [키-값 테이블이 잡동사니 저장소가 됨] → 키를 상수로 정의하고 용도를 문서화한다. 늘어나면 그때 분리한다.

## Open Questions

- 안전한 `maxRequestsPerRun` 실측값 — 3회차의 `pagesRequested` 기록이 며칠 쌓여야 정할 수 있다. 그게 이 change 이후의 관측 과제다.
- 법원별로 물건 수 편차가 크면(서울중앙 444행 vs 소규모 지원) 법원 단위 예산이 비효율적일 수 있다. 실제 편차를 보고 판단한다.
