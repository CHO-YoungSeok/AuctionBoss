# Proposal: hardening-round1

## Why

아홉 사이클을 거치며 기능은 갖춰졌지만, **각 사이클의 리뷰는 그 사이클의 변경분만** 봤다. 사이클 간 상호작용과 누적된 부채는 아무도 보지 않았다. 그리고 지금까지 발견된 심각한 결함들의 공통점이 하나 있다 — **전부 테스트를 통과하면서 숨어 있었다.**

| 결함 | 발견 경로 |
|---|---|
| `analyzed=` 빈 값이 전체 물건 반환 | 리뷰(코드 대조) |
| `null → 값` 변경이 화면·재분석에서 소실 | 리뷰 |
| 재분석이 미분석 물건에 밀려 영구 미실행 | 리뷰 (294개 테스트 통과 중) |
| `pagesRequested`가 관측값이 아닌 설정 상수 | 오케스트레이터 검토 |
| **zod 스키마가 확장 필드 32개를 조용히 폐기** | **실데이터로 보고서를 읽어서** |
| **`min_area > max_area` 48%, 면적당 가격 143배 오차** | **실데이터 직접 질의** |

마지막 두 개는 코드를 아무리 읽어도 안 나왔다. **실데이터와 실행이 있어야만 드러나는 종류**다.

이 사이클은 **알려진 미방어 지점을 닫고, 아직 아무도 확인하지 않은 경로를 실데이터로 훑는다.**

## What Changes

- **알려진 미방어 지점 보강** (앞선 리뷰들이 "여전히 방어가 없다"고 명시한 것들):
  - 서버 컴포넌트를 실제로 렌더링하는 테스트가 **하나도 없다.** 필드 유실·배지 표시가 JSX에 실제로 배선됐는지는 타입 검사와 수동 curl에만 의존한다. 최소한의 렌더 테스트 인프라를 만든다.
  - `NEEDS_ANALYSIS_PREDICATE` SQL의 "변경 시각 == 분석 시각" 경계 테스트가 없다.
  - `AnalysisBody`가 상세 페이지에 **아직 배선되지 않았다**(8회차가 소유권 때문에 넘긴 인수인계 항목). 지금은 여전히 `<pre>`로 렌더된다.
- **다른 워커·경로의 같은 결함 유형 수색**: zod 스키마가 조용히 필드를 버리는 문제가 `workers/lib/api.ts`에서 발견됐다. **같은 패턴이 다른 곳에도 있는지** 전수 확인한다 — 스키마와 도메인 타입이 어긋나면 조용히 데이터가 사라진다.
- **실데이터 전 경로 훑기**: 389건이 있는 상태에서 모든 화면·API·워커를 실제로 돌려 예외 경로를 밟는다. 지금까지 각 사이클은 자기 기능만 확인했다.
- **누적된 개선 항목 처리**: 아카이브된 change들의 Open Questions와 리뷰가 "기록만 하고 넘긴" 항목들을 모아 판단한다. 고칠 것은 고치고, 여전히 근거가 없는 것은 그렇다고 명시한다.

비목표: 새 기능, 9회차 Phase 2(별도 change), 프롬프트 품질 개선(별도 이슈).

## Capabilities

### New Capabilities

(없음)

### Modified Capabilities

발견된 결함에 따라 결정한다. **스펙 변경이 필요한 결함이 나오면 그때 delta spec을 추가하고, 순수 결함 수정이면 스펙은 건드리지 않는다.**

## Impact

- 테스트 인프라가 늘어난다(서버 컴포넌트 렌더 테스트). 이 프로젝트에 없던 종류라 도입 비용이 있다.
- 발견되는 결함에 따라 범위가 달라진다 — **이 change는 발견 주도적이다.** 계획 단계에서 무엇을 고칠지 전부 알 수 없다는 것이 전제다.
- 실제 사이트 요청은 최소로 한다. 이미 389건이 있으므로 새 수집이 거의 필요 없다.
