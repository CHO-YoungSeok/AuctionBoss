## Why

메인 스펙 9개를 코드와 대조했더니 6개에 코드와 다른 서술이 있었다. 대부분은 이후 change가 코드와 설정만 바꾸고 메인 스펙을 고치지 않아 생긴 낡은 서술이고, 일부는 스펙 안에서 서로 모순된다(예: 화면의 분석 최신성 판정이 "재분석 대상 선정과 같은 규칙"이어야 한다면서, 대상 선정에는 쿨다운이 있다).
스펙은 이 저장소에서 "시스템이 무엇을 해야 하는가"의 기준이고, 다음 단계(쓰기 API 이식)가 이 스펙을 계약으로 삼는다. 기준이 틀린 채로 다음 단계를 시작하면 틀린 계약을 옮기게 되므로, 먼저 스펙을 지금 코드의 실제 동작에 맞춘다.

## What Changes

이 change는 **스펙 문서만 고친다. 코드 동작은 바꾸지 않는다.** 아래는 모두 "코드가 옳고 스펙이 틀린" 경우다.

- **auction-analysis**
  - 화면의 분석 최신성 판정은 재분석 대상 규칙에서 **쿨다운만 뺀** 같은 규칙이라고 명시한다(스펙 내부 모순 해소).
  - 재분석 조건을 "낡은 프롬프트 버전"에서 "현재와 **다른** 프롬프트 버전"으로 고친다.
  - 분석 실행을 "Claude Code 분석 실행"에서 "Claude 분석 실행"으로 바꾸고, **API 키가 있으면 Messages API, 없으면 CLI**를 쓰는 우선순위를 명시한다.
  - 이전 분석은 최신 1건 외에 최근 일부만 본문을 보여 준다는 표시 한도를 명시한다.
- **auction-collection**
  - 낡은 "1단계 기본값은 지역 1곳" 서술을 지운다.
  - 회차당 요청 수 안전장치를 요구사항으로 추가한다(진행 중인 법원은 끊지 않고, 다음 법원을 시작하지 않는다).
- **auction-viewing**
  - 키워드 검색 범위를 "소재지·사건번호·건물명"으로 통일한다(시나리오가 "소재지만"이라고 해 요구사항과 모순).
  - 물건 조회 API의 파라미터 목록을 현재 코드에 맞춘다(court, minDiscountRate, hasPhotos, excludePast, needsAnalysis, 억·만원 가격 입력, pageSize 최대 200 등).
  - 저감률 필터 시나리오를 실제 규칙(유찰 여부와 무관하게 감정가 대비 저감률로 판정)에 맞춘다.
- **deployment-and-health**: 이 capability의 범위가 Next.js 웹 앱의 배포와 헬스체크임을 명시하고, Spring 백엔드는 spring-backend가 다룬다고 참조한다.
- **run-observability**
  - 차단 상태 판정 문구를 코드에 맞춘다(마지막 완료 회차가 차단이면 차단).
  - 실행이 겹쳐 회차를 건너뛸 때 기록하는 범위를 실제와 맞춘다(수집 워커).
- **auction-history**
  - 기준점은 감시 필드마다 한 행이며 값이 없는 필드는 남기지 않는다고 명시한다.
  - "최근 변동"의 기간(7일)을 명시한다.
- **spring-backend**
  - 시드 미적재 조건을 "운영 설정"이 아니라 "시드 설정이 켜지지 않은 경우"로 고친다(운영 프로필은 아직 없음).
  - 재분석 대상 조회의 정렬 규칙(가장 오래 전에 분석된 물건 우선)을 추가한다.
  - 지역 파라미터(sido, sigungu)가 여러 값을 받는다는 점을 명시한다.

**이 change에서 하지 않는 것 (후속 change로 분리)**
- 코드 결함 수정: 사진 워커의 회차 기록, 수집 워커와의 차단 백오프 공유, 실패 재시도 간격, 소스 어댑터 우회
- 배포 설정 결함: compose와 K8s의 분석 워커 주소 변수 이름(`BASE_URL` vs `AUCTIONBOSS_API_BASE`), Next 이미지 헬스체크의 curl 부재
- 위 결함과 관련된 스펙 요구사항(item-photos의 백오프 공유, run-observability의 백오프 공유 등)은 **지금 문구를 그대로 둔다.** 스펙이 옳고 코드가 틀린 경우라서, 코드를 고치는 change에서 함께 다룬다.

### Modified Capabilities
- `auction-analysis`: 분석 대상 선정, Claude 분석 실행, 분석 결과 표시 요구사항의 서술을 코드에 맞춤
- `auction-collection`: 수집 범위 설정 요구사항에 회차당 요청 수 안전장치를 추가하고 낡은 서술 제거
- `auction-viewing`: 물건 목록 열람(키워드·저감률 시나리오)과 물건 조회 API(파라미터 목록) 요구사항을 코드에 맞춤
- `deployment-and-health`: 헬스체크 엔드포인트 요구사항에 범위(Next 웹 앱)를 명시
- `run-observability`: 실행 회차 기록(건너뜀 범위)과 실행 상태 판정(차단 판정) 요구사항을 코드에 맞춤
- `auction-history`: 변경 이력 기록(기준점 단위)과 변경 이력 표시(최근 변동 기간) 요구사항을 코드에 맞춤
- `spring-backend`: 더미 시드 데이터(미적재 조건)와 물건 목록 API 호환(재분석 정렬, 지역 복수값) 요구사항을 보완

## Impact

- **바뀌는 파일**: `openspec/specs/` 아래 메인 스펙 7개(아카이브 시 동기화)와 auction-analysis 메인 스펙의 Purpose 문구. 코드 동작과 설정은 바뀌지 않는다.
- **테스트 추가**: 이번에 스펙에 새로 명시한 규칙 중 테스트가 없는 두 가지(API 키 유무에 따른 Claude 실행 방식 선택, 상세 화면의 이전 분석 표시 한도)에 회귀 테스트만 더한다. 동작은 그대로다.
- **검증**: 고친 문장마다 근거가 되는 코드 위치와 그 동작을 지키는 테스트를 대조한다. 게이트(타입 검사, TS 테스트, 빌드, 린트, Gradle check)는 코드가 그대로이므로 그대로 통과해야 한다.
- **다음 단계와의 관계**: 로드맵 2단계(쓰기 API 이식)와 사진 워커·배포 설정 결함 수정 change가 이 스펙을 기준으로 삼는다.
