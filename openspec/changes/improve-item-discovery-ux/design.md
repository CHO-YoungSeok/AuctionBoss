# Design: improve-item-discovery-ux

## Context

동기는 proposal.md 참조. 이 change는 **데이터 계층을 건드리지 않는다.** 필요한 값이 이미 전부 저장되어 있다:

- 감정가·최저가(1회차), 면적·차수별 최저가·구조화 소재지(4회차), 변경 이력·분석 이력(2회차), 관심 여부(5회차).
- 계산 로직도 있다: `computePricePerArea`(`src/lib/domain/price.ts`, 4회차에 UI·워커 공용으로 옮김), `bidRatio` 정렬 표현식(`repository.ts`, 1회차).
- 표시 헬퍼 관례: `src/app/_lib/*.ts`에 순수 함수로 추출하고 테스트한다(인라인 JSX 판정 때문에 버그가 배포된 전례가 있다).
- 클라이언트 JS를 쓰지 않는 것이 프로젝트 규칙이다.

딥링크 조사 결과(2026-09-08, 요청 3회): 법원경매정보는 WebSquare5 SPA이고 물건 식별자가 URL로 전달되지 않는다. 상세 화면 XML 171KB에 `location.search`/`location.hash`/`URLSearchParams`가 **0건**이다. `index.on?w2xPath=...`로 화면 선택은 되지만 물건 지정 파라미터가 없다.

## Goals / Non-Goals

**Goals:**
- 분석을 기다리지 않고도 1차 선별이 가능하게
- 원본 확인 경로를 정직하게 제공
- 상세를 사람이 물건을 보는 순서로 재배치

**Non-Goals:**
- 데이터 계층·API·필터 파라미터 변경
- 사진, 지역 필터, 평 단위, 가격 필터 개선 — 9회차 이슈
- 클라이언트 JS 도입

## Decisions

### D1. 목록에 지표 2개만 추가: 저감률과 면적당 가격

열을 무한히 늘리지 않는다. 목록에서 "이 물건을 더 볼지" 판단하는 데 실제로 쓰이는 것만 넣는다.

- **저감률**(최저가 ÷ 감정가): 유찰이 몇 번 돌았는지를 한 숫자로 요약한다. 유찰횟수 열이 이미 있지만, 100%·80%·64%라는 **금액 감각**은 횟수로 대체되지 않는다.
- **면적당 가격**: 물건 간 비교의 유일한 공통 척도다. 총액만으로는 84㎡ 5억과 30㎡ 3억을 비교할 수 없다.
- 이 둘을 넣는 대신 이미 있는 감정가 열은 유지한다(저감률의 분모라 함께 보여야 의미가 있다).
- 저감률은 **단계별로 시각 구분**한다(예: 100% / 80%대 / 64%대 / 그 이하). 숫자만 나열하면 훑을 때 눈에 걸리지 않는다. 색만으로 구분하지 않고 텍스트도 함께 둔다.

### D2. 원본 링크: 홈으로 보내되 검색값을 그 자리에서 준다

물건별 GET URL이 없다는 것이 확인됐으므로(Context), 선택지는 셋뿐이다: (a) 링크를 안 준다 (b) `w2xPath`로 상세 화면을 강제로 연다 (c) 홈으로 보낸다.

**(c)를 택한다.** (b)는 화면은 뜨지만 `csNo`/`cortOfcCd`가 없어 데이터 없는 빈 화면이나 오류가 될 가능성이 높다 — 사용자에게 깨진 링크를 주는 것은 링크가 없는 것보다 나쁘다. (a)는 사용자가 원본을 봐야 하는 실제 필요를 방치한다.

- 상세 페이지에 "법원경매정보에서 확인" 블록을 둔다: 홈 링크 + **법원명과 사건번호를 선택·복사하기 쉬운 형태**(`<input readonly>`)로 나란히 + "이 값으로 검색하세요" 한 줄.
- **왜 `<input readonly>`인가**: 클립보드 복사는 JS가 필요하다. `input`은 클릭 한 번으로 전체 선택이 되므로 JS 없이 복사에 가장 가깝다. 텍스트로 두면 사용자가 드래그로 정확히 집어내야 한다.
- 딥링크가 불가능하다는 사실을 화면에 구구절절 쓰지 않는다. 사용자에게 필요한 건 "여기서 이걸 검색하라"이지 그 사이트의 구현 사정이 아니다.

### D3. 분석 상태를 3가지로 구분해 표시

지금은 분석이 있으면 보여주고 없으면 "분석 대기 중"뿐이다. 재분석 대상(2회차)이라는 상태가 있는데 화면에 없다.

- **대기 중**(분석 없음) / **최신**(분석 있고 재분석 대상 아님) / **갱신 예정**(분석 있으나 값이 바뀌었거나 프롬프트 버전이 낡음).
- "갱신 예정"이 중요한 이유: 사용자가 보고 있는 분석이 **현재 가격 기준이 아닐 수 있다**는 경고다. 2회차에서 "최저가가 30% 떨어진 뒤에도 옛 가격 기준 분석이 남아 있으면 틀린 정보"라고 적었는데, 지금 화면은 그걸 알려주지 않는다.
- 판정은 이미 있는 `needsAnalysis` 로직을 재사용한다. 새 판정 규칙을 만들지 않는다 — 두 벌이 되면 화면과 워커가 다른 답을 낸다.
- 대기 순번 같은 것은 만들지 않는다. 재분석·쿨다운·한도가 얽혀 있어 정확한 예측이 불가능하고, 틀린 예측은 없느니만 못하다.

### D4. 상세 재배치: 판단 순서를 따른다

현재는 수집 필드 순서다. 사람이 경매 물건을 볼 때의 순서로 바꾼다:

1. **가격** — 감정가·최저가·저감률·면적당 가격·차수별 추이
2. **물건 개요** — 용도·면적·소재지·매각기일
3. **AI 분석** — 상태 배지와 함께
4. **변경 이력** — 무엇이 언제 바뀌었나
5. **원본 확인** — D2 블록
6. **부가 정보** — 담당계, 사건 비고, 코드값 등

- 재배치일 뿐 정보를 지우지 않는다. 4회차에서 확장 필드 32개를 표시하게 만들었고, 그중 무엇이 덜 중요한지는 아직 사용자가 써본 근거가 없다. 순서만 바꾸고 판단은 9회차로 미룬다.

### D5. 목록의 소재지: 구조화 값으로 지역을 앞세운다

소재지 전체 문자열이 길어 잘리면 어느 동네인지 알 수 없다. 4회차의 `sido`/`sigungu`/`dong`을 써서 **지역을 짧게 앞에 두고 나머지 주소를 뒤에** 붙인다.

- 구조화 값이 없는 물건(이 기능 이전 수집분)은 기존 `address`를 그대로 쓴다. 값이 없다고 화면이 비면 안 된다.
- 지역으로 **필터**하는 것은 9회차다. 여기서는 표시만 한다 — 목록 쿼리의 `WHERE`를 건드리면 1회차의 필터·정렬 테스트 전체가 회귀 위험에 들어간다.

## Risks / Trade-offs

- [목록 열이 많아져 가로로 넘침] → 지표 2개만 추가하고 소재지를 요약해 상쇄한다. 그래도 좁으면 우선순위가 낮은 열을 접는 것은 9회차에서 실제로 써보고 정한다.
- [저감률 시각 구분이 색에만 의존하면 접근성 문제] → 텍스트 라벨을 함께 둔다.
- [분석 상태 판정이 워커와 어긋남] → `needsAnalysis` 로직을 재사용하고, 화면용으로 다시 구현하지 않는다.
- [상세 재배치가 기존 사용자의 기대를 깬다] → 아직 사용자가 없다. 지금이 바꾸기 가장 싼 시점이다.

## Open Questions

- 저감률 구간을 몇 단계로 나눌지 — 실제 데이터 분포를 보고 정한다. 상수라 바꾸기 쉽다.
- 목록에서 면적당 가격이 없는 물건(면적 미상)이 얼마나 되는지 — 많으면 열의 가치가 떨어진다. 실데이터로 확인 후 9회차에서 재검토.
