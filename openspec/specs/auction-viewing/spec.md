# auction-viewing Specification

## Purpose

수집된 법원경매 물건을 웹에서 열람할 수 있게 한다. 목록에서 물건을 훑어보고 상세에서 개별 물건 정보와 AI 분석 결과를 확인하는 것이 핵심 사용 흐름이다.

## Requirements

### Requirement: 물건 목록 열람
시스템은 저장된 물건의 목록 페이지를 제공해야 한다(SHALL). 목록에는 최소한 소재지, 용도, 감정가, 최저매각가격, 매각기일, 유찰횟수, 진행상태가 표시되어야 하며(SHALL), 매각기일 오름차순을 기본 정렬로 하고 페이지네이션을 지원해야 한다(SHALL).

목록 페이지는 용도(다중 선택), 최저매각가격 범위, 유찰횟수 최소값, 소재지 키워드로 결과를 좁히는 필터를 제공해야 한다(SHALL). 정렬 기준(매각기일, 최저매각가격, 감정가 대비 최저가 비율, 유찰횟수)과 방향(오름/내림차순)을 사용자가 선택할 수 있어야 한다(SHALL). 적용된 필터·정렬·페이지 상태는 URL에 반영되어야 하며(MUST), 그 URL을 다시 열면 같은 결과가 재현되어야 한다(SHALL).

목록의 각 물건은 관심 목록에 담겼는지 알 수 있어야 하며(SHALL), 목록에서 바로 담고 뺄 수 있어야 한다(SHALL). 관심 여부 표시가 기존 필터·정렬·전체 건수 계산에 영향을 주어서는 안 된다(MUST NOT).

목록은 분석 결과가 없어도 1차 선별이 가능하도록 판단 지표를 표시해야 한다(SHALL): 감정가 대비 최저매각가격 비율과 면적당 최저매각가격. 저감 비율은 단계를 훑어서 알아볼 수 있게 시각적으로 구별되어야 하며(SHALL), 색에만 의존해서는 안 된다(MUST NOT).

소재지는 길이 때문에 잘려 지역을 알 수 없게 되어서는 안 된다(MUST NOT). 구조화된 소재지가 있으면 지역을 앞세워 요약 표시하고, 없으면 기존 소재지 문자열을 그대로 쓴다(SHALL).

목록은 시/도·시군구로 결과를 좁히는 지역 필터를 제공해야 한다(SHALL). 선택지는 저장된 데이터에서 도출해야 하며(SHALL), 고정 목록이어서는 안 된다(MUST NOT) — 수집 법원이 늘면 지역도 늘어난다.

용도 필터는 소스가 복합 문자열로 주는 용도를 **개별 용도 단위로** 다뤄야 한다(SHALL). 복합 문자열 전체와 정확히 일치하는 것만 걸러서는 안 된다(MUST NOT) — 그렇게 하면 해당 용도를 포함한 물건 대부분이 결과에서 조용히 빠진다.

가격 조건은 사람이 읽고 쓰는 단위로 입력할 수 있어야 하며(SHALL), 자주 쓰는 가격대를 한 번에 적용할 수단을 제공해야 한다(SHALL).

매각기일 범위와 관심 물건 여부로 결과를 좁힐 수 있어야 한다(SHALL). 이 조건들은 모두 선택적이어야 하며, 지정하지 않았을 때의 결과가 이 변경 이전과 달라져서는 안 된다(MUST NOT).

적용 중인 필터가 무엇인지 한눈에 보여야 하고(SHALL), 개별 조건을 따로 해제할 수 있어야 한다(SHALL). 페이지 크기를 선택할 수단을 제공해야 한다(SHALL).

#### Scenario: 목록 조회
- **WHEN** 사용자가 물건 목록 페이지에 접속하면
- **THEN** 저장된 물건들이 매각기일이 가까운 순으로 페이지 단위로 표시된다

#### Scenario: 물건이 없는 경우
- **WHEN** 아직 수집된 물건이 없는 상태에서 목록 페이지에 접속하면
- **THEN** 오류 대신 "물건이 없다"는 안내가 표시된다

#### Scenario: 용도로 필터
- **WHEN** 사용자가 용도 필터에서 하나 이상의 용도를 선택하면
- **THEN** 선택한 용도에 해당하는 물건만 표시되고, 전체 건수도 필터 적용 후 기준으로 표시된다

#### Scenario: 가격 범위로 필터
- **WHEN** 사용자가 최저매각가격의 최소값·최대값을 지정하면
- **THEN** 그 범위 안의 물건만 표시된다. 한쪽만 지정하면 그 방향으로만 제한된다

#### Scenario: 소재지 키워드 검색
- **WHEN** 사용자가 소재지 키워드를 입력하면
- **THEN** 소재지에 그 키워드를 포함하는 물건만 표시된다

#### Scenario: 정렬 변경
- **WHEN** 사용자가 정렬 기준과 방향을 선택하면
- **THEN** 목록이 그 기준으로 정렬되고, 값이 없는(null) 물건은 정렬 방향과 무관하게 뒤에 배치된다

#### Scenario: 필터 결과가 없는 경우
- **WHEN** 적용된 필터에 맞는 물건이 하나도 없으면
- **THEN** 오류 대신 조건에 맞는 물건이 없다는 안내와 필터를 초기화할 수단이 표시된다

#### Scenario: 필터 상태가 URL에 보존됨
- **WHEN** 사용자가 필터·정렬을 적용한 뒤 그 URL을 새로 열거나 공유하면
- **THEN** 같은 필터·정렬·페이지가 적용된 동일한 결과가 표시된다

#### Scenario: 선택 가능한 용도 목록
- **WHEN** 목록 페이지가 용도 필터를 표시하면
- **THEN** 선택지는 현재 저장된 물건들에 실제로 존재하는 용도에서 도출된다(고정 목록이 아니다)
#### Scenario: 목록에서 관심 표시
- **WHEN** 관심 목록에 담긴 물건과 담기지 않은 물건이 함께 표시되면
- **THEN** 담긴 물건을 구별할 수 있고, 각 행에서 담고 빼는 조작을 할 수 있다

#### Scenario: 관심 표시가 필터에 영향 없음
- **WHEN** 필터와 정렬이 적용된 목록에서 관심 여부가 표시되면
- **THEN** 필터 결과와 전체 건수가 관심 여부와 무관하게 이전과 동일하다
#### Scenario: 판단 지표 표시
- **WHEN** 감정가·최저가·면적이 있는 물건이 목록에 표시되면
- **THEN** 감정가 대비 비율과 면적당 가격이 함께 표시된다

#### Scenario: 지표를 계산할 수 없는 물건
- **WHEN** 면적이나 감정가가 없어 지표를 계산할 수 없으면
- **THEN** 그 칸은 없음으로 표시되고 행 전체는 정상 렌더링된다

#### Scenario: 지역 요약
- **WHEN** 구조화된 소재지가 있는 물건과 없는 물건이 함께 표시되면
- **THEN** 전자는 지역이 앞세워져 표시되고, 후자도 오류 없이 기존 소재지가 표시된다
#### Scenario: 지역으로 필터
- **WHEN** 사용자가 특정 시군구를 선택하면
- **THEN** 그 지역 물건만 표시되고 전체 건수도 그 기준으로 계산된다

#### Scenario: 복합 용도 문자열 매칭
- **WHEN** 소스가 여러 용도를 한 문자열로 준 물건이 있고 사용자가 그중 한 용도를 선택하면
- **THEN** 그 물건이 결과에 포함된다

#### Scenario: 지정하지 않은 새 조건은 결과를 바꾸지 않음
- **WHEN** 새로 추가된 조건을 지정하지 않고 목록을 조회하면
- **THEN** 이 변경 이전과 동일한 결과와 전체 건수가 반환된다

#### Scenario: 필터로 결과가 0건일 때
- **WHEN** 새로 추가된 어떤 필터로도 결과가 0건이 되면
- **THEN** 물건이 없다는 안내가 아니라 조건에 맞는 물건이 없다는 안내와 초기화 수단이 표시된다

#### Scenario: 필터 상태 표시와 개별 해제
- **WHEN** 여러 조건이 적용된 상태에서 목록을 보면
- **THEN** 적용 중인 조건이 각각 보이고, 하나만 해제해도 나머지가 유지된다

#### Scenario: 페이지 이동 시 조건 보존
- **WHEN** 조건이 적용된 목록에서 다음 페이지로 이동하면
- **THEN** 모든 조건이 그대로 유지된다

### Requirement: 물건 상세 열람
시스템은 개별 물건의 상세 페이지를 제공해야 한다(SHALL). 상세에는 목록 표시 항목에 더해 사건번호, 물건번호, 담당 법원, 수집 시각이 표시되어야 한다(SHALL).

수집된 확장 정보도 표시되어야 한다(SHALL): 면적과 건물 구조, 차수별 최저매각가격, 용도 분류, 구조화된 소재지, 매각기일 시각·장소, 사건 비고, 담당계 연락처. 값이 없는 항목은 없음을 알 수 있게 표시해야 하며(SHALL), 값이 없다는 이유로 화면이 오류가 나서는 안 된다(MUST NOT).

소스가 여러 줄로 주는 값(건물 구조·면적 서술 등)은 줄바꿈이 보존되어 읽을 수 있게 표시되어야 한다(SHALL).

상세 페이지에서도 관심 목록에 담고 뺄 수 있어야 하며(SHALL), 현재 담긴 상태가 표시되어야 한다(SHALL).

상세 페이지는 원본 확인 경로를 제공해야 한다(SHALL): 법원경매정보 사이트로 가는 링크와, 그곳에서 이 물건을 찾는 데 필요한 값(법원명·사건번호)을 선택·복사하기 쉬운 형태로 함께 제공한다. 동작하지 않는 링크를 제공해서는 안 된다(MUST NOT).

상세 정보는 판단 순서(가격 → 물건 개요 → AI 분석 → 변경 이력 → 원본 확인 → 부가 정보)로 배치되어야 한다(SHALL). 재배치로 기존에 표시되던 정보가 사라져서는 안 된다(MUST NOT).

사건 비고는 가격 정보보다 먼저 보이는 위치에 원문 그대로 표시되어야 한다(SHALL) — 입찰 가부를 가르는 내용이 다른 정보를 모두 검토한 뒤에야 발견되어서는 안 된다.

면적당 가격을 표시할 때는 **어느 면적을 기준으로 계산했는지 함께 밝혀야 한다**(MUST). 최소·최대 면적이 다른 물건에서 기준을 밝히지 않으면 사용자가 검증할 수 없다.

매각기일 시각처럼 소스가 준 원문이 사람이 읽기 어려운 형식이면 표시 계층에서 읽을 수 있는 형태로 변환해야 한다(SHALL). 원문 보존은 저장 계층의 규칙이며 표시 계층까지 적용되는 것은 아니다.

수집된 사진이 있으면 표시되어야 한다(SHALL). 사진이 없는 것은 정상 상태이며 오류로 보여서는 안 된다(MUST NOT). 사진의 수집 상태는 `item-photos` capability가 정의한다.

#### Scenario: 상세 조회
- **WHEN** 사용자가 목록에서 물건을 선택하면
- **THEN** 해당 물건의 상세 정보 페이지가 표시된다

#### Scenario: 존재하지 않는 물건
- **WHEN** 존재하지 않는 물건 ID로 상세 페이지에 접근하면
- **THEN** 404(찾을 수 없음) 응답이 반환된다

#### Scenario: 확장 정보 표시
- **WHEN** 면적·차수별 최저가·용도 분류가 수집된 물건의 상세 페이지를 열면
- **THEN** 그 값들이 사람이 읽을 수 있는 형태로 표시된다

#### Scenario: 확장 정보가 없는 물건
- **WHEN** 확장 필드가 비어 있는 물건(이 기능 이전에 수집된 물건 포함)의 상세 페이지를 열면
- **THEN** 오류 없이 기존 정보가 정상 표시되고 없는 항목은 없음으로 표시된다

#### Scenario: 여러 줄 값 표시
- **WHEN** 건물 구조·면적처럼 줄바꿈이 포함된 값을 표시하면
- **THEN** 줄바꿈이 보존되어 한 줄로 뭉개지지 않는다
#### Scenario: 상세에서 관심 토글
- **WHEN** 상세 페이지에서 관심 담기를 하면
- **THEN** 담긴 상태로 바뀌고 같은 상세 페이지가 유지된다
#### Scenario: 원본 확인 경로
- **WHEN** 사용자가 상세 페이지에서 원본 확인 영역을 보면
- **THEN** 법원경매정보로 가는 링크와 함께 법원명·사건번호가 복사하기 쉬운 형태로 제공되고, 그 값으로 검색하라는 안내가 있다

#### Scenario: 재배치 후 정보 보존
- **WHEN** 확장 필드까지 채워진 물건의 상세를 열면
- **THEN** 재배치 이전에 표시되던 모든 항목이 여전히 표시된다
#### Scenario: 비고 우선 표시
- **WHEN** 사건 비고가 있는 물건의 상세를 열면
- **THEN** 비고가 가격 정보보다 위에서 원문 그대로 보인다

#### Scenario: 면적당 가격의 기준 표시
- **WHEN** 최소·최대 면적이 다른 물건의 면적당 가격이 표시되면
- **THEN** 어느 면적으로 계산했는지 함께 표시된다

#### Scenario: 매각기일 시각 표시
- **WHEN** 소스가 매각기일 시각을 네 자리 숫자로 준 물건의 상세를 열면
- **THEN** 시:분 형태로 읽을 수 있게 표시된다
#### Scenario: 사진 표시
- **WHEN** 사진이 수집된 물건의 상세를 열면
- **THEN** 사진이 물건 정보와 함께 표시된다

### Requirement: 물건 조회 API
시스템은 물건 목록과 상세를 JSON으로 반환하는 HTTP API를 제공해야 한다(SHALL). 목록 API는 페이지네이션 파라미터와 미분석 물건 필터를 지원해야 한다(SHALL) — 미분석 필터는 분석 워커가 분석 대상을 조회하는 데 사용된다.

목록 API는 용도, 최저매각가격 범위, 유찰횟수 최소값, 소재지 키워드 필터와 정렬 기준·방향 파라미터를 지원해야 한다(SHALL). 새 파라미터는 모두 선택적이어야 하며, 생략 시 기존과 동일하게 동작해야 한다(MUST) — 기존 클라이언트(분석 워커 포함)가 영향을 받아서는 안 된다(MUST NOT). 인식할 수 없거나 허용 범위를 벗어난 파라미터 값은 400으로 거부해야 한다(SHALL).

목록 API는 지역, 매각기일 범위, 관심 물건 여부 필터와 면적당 가격 정렬을 지원해야 한다(SHALL). 새 파라미터는 모두 선택적이어야 한다(MUST).

용도 필터의 매칭 규칙이 개별 용도 단위로 바뀌므로, 같은 요청이 이전보다 넓은 결과를 반환한다. 이는 의도된 계약 변경이며 문서에 반영되어야 한다(SHALL).

정렬에서 값이 없는 물건은 정렬 방향과 무관하게 뒤에 배치되어야 한다(SHALL).

#### Scenario: 목록 API 조회
- **WHEN** 클라이언트가 목록 API를 호출하면
- **THEN** 물건 배열과 페이지네이션 정보(전체 건수 포함)가 JSON으로 반환된다

#### Scenario: 미분석 물건 필터
- **WHEN** 클라이언트가 미분석 필터를 지정해 목록 API를 호출하면
- **THEN** 분석 결과가 아직 없는 물건만 반환된다

#### Scenario: 필터 파라미터 조합
- **WHEN** 클라이언트가 용도·가격범위·유찰횟수·키워드 필터를 함께 지정하면
- **THEN** 모든 조건을 동시에 만족하는 물건만 반환되고, 전체 건수도 그 조건 기준으로 계산된다

#### Scenario: 기존 계약 유지
- **WHEN** 새 필터 파라미터 없이 기존 방식(`analyzed`, `page`, `pageSize`)으로만 호출하면
- **THEN** 이 변경 이전과 동일한 결과와 응답 형태가 반환된다

#### Scenario: 잘못된 필터 값
- **WHEN** 정렬 기준에 허용되지 않은 값이나 숫자가 아닌 가격이 지정되면
- **THEN** 400 오류와 어떤 파라미터가 잘못됐는지 알려주는 응답이 반환된다
#### Scenario: 면적당 가격 정렬
- **WHEN** 클라이언트가 면적당 가격 기준으로 정렬을 요청하면
- **THEN** 그 기준으로 정렬되고, 면적이 없어 계산할 수 없는 물건은 방향과 무관하게 뒤에 온다

#### Scenario: 새 파라미터 미지정 시 기존 동작
- **WHEN** 새 파라미터 없이 기존 방식으로만 호출하면
- **THEN** 이 변경 이전과 동일한 결과와 응답 형태가 반환된다

### Requirement: 용도 목록 조회
시스템은 현재 저장된 물건에 존재하는 용도 목록을 조회할 수단을 제공해야 한다(SHALL). 목록은 중복 없이 반환되어야 하며(MUST), 저장된 물건이 없으면 빈 목록을 반환해야 한다(SHALL).

#### Scenario: 용도 목록 반환
- **WHEN** 저장된 물건에 아파트·다세대·오피스텔이 존재하는 상태에서 용도 목록을 조회하면
- **THEN** 그 세 용도가 중복 없이 반환된다

#### Scenario: 물건이 없을 때
- **WHEN** 저장된 물건이 없는 상태에서 용도 목록을 조회하면
- **THEN** 오류 없이 빈 목록이 반환된다
