# auction-analysis Specification

## Purpose

수집된 경매 물건을 Claude로 분석하고(API 키가 있으면 Messages API, 없으면 서버 로컬의 Claude Code CLI) 그 결과를 서비스에 저장·표시하는 파이프라인을 제공한다. 분석 품질(프롬프트)은 이후 계속 발전시키되, 이 capability는 "대상 선정 → 실행 → 결과 저장 → 표시"의 흐름을 계약으로 고정한다.

## Requirements

### Requirement: 분석 대상 선정
분석 워커는 분석이 필요한 물건을 조회해 분석 대상으로 삼아야 한다(SHALL). 분석이 필요한 물건은 다음 세 가지다:

1. 분석 결과가 아직 없는 물건
2. 최신 분석 이후 감시 대상 필드가 변경된 물건 — 최저가가 떨어진 뒤에도 옛 가격 기준 분석이 남아 있으면 틀린 정보가 되기 때문이다
3. 최신 분석이 워커의 현재 프롬프트 버전과 다른 버전으로 생성된 물건 — 버전의 높고 낮음은 비교하지 않고 같은지 다른지만 본다

한 실행 회차에서 처리할 최대 물건 수는 설정으로 제한할 수 있어야 한다(SHALL) — 분석 비용(Claude 호출 수)을 통제하기 위함이다. 신규 분석과 재분석의 회차당 건수는 각각 제한할 수 있어야 하며(SHALL), 신규 물건 분석이 재분석보다 우선해야 한다(SHALL) — 아직 한 번도 분석되지 않은 물건이 재분석 대기열에 밀려 무한히 미뤄져서는 안 된다(MUST NOT).

기존 `analyzed` 필터의 의미(분석 결과 유무)는 바뀌지 않아야 하며(MUST NOT), 재분석 대상 조회는 별도 수단으로 제공되어야 한다(SHALL).

재분석 대상 조회는 **아직 한 번도 분석되지 않은 물건을 포함해서는 안 된다**(MUST NOT) — 그런 물건은 신규 분석 경로가 담당하며, 재분석 경로에 섞이면 재분석 한도를 잠식해 실제 재분석 대상이 영구히 처리되지 않는다.

같은 물건이 짧은 간격으로 반복 재분석되어서는 안 된다(MUST NOT). 최신 분석이 설정된 최소 간격보다 최근이면 그 물건은 재분석 대상에서 제외되어야 한다(SHALL) — 소스가 감시 필드를 회차마다 뒤집어 보고하면 매 회차가 유효한 변경으로 기록되어 유료 호출이 무한히 유발되므로, 회차당 건수 제한만으로는 비용이 통제되지 않는다.

#### Scenario: 미분석 물건 선정
- **WHEN** 분석 워커가 실행되면
- **THEN** 미분석 물건이 회차당 최대 건수 이내로 조회되어 순차 분석된다

#### Scenario: 분석할 물건이 없는 경우
- **WHEN** 미분석 물건이 없고 재분석 대상도 없는 상태에서 워커가 실행되면
- **THEN** 아무 분석도 실행하지 않고 정상 종료한다

#### Scenario: 변경된 물건 재분석
- **WHEN** 이미 분석된 물건의 최저매각가격이 변경된 뒤 워커가 실행되면
- **THEN** 그 물건이 재분석 대상으로 선정되어 다시 분석된다

#### Scenario: 프롬프트 버전 갱신에 따른 재분석
- **WHEN** 저장된 최신 분석의 프롬프트 버전이 워커의 현재 프롬프트 버전과 다른 상태에서 워커가 실행되면
- **THEN** 그 물건이 재분석 대상으로 선정된다

#### Scenario: 미분석 물건은 재분석 대상에 섞이지 않음
- **WHEN** 아직 분석되지 않은 물건이 다수 있고 실제 재분석 대상도 하나 있는 상태에서 재분석 대상을 조회하면
- **THEN** 미분석 물건은 결과에 포함되지 않고 실제 재분석 대상이 반환된다

#### Scenario: 최근에 분석된 물건은 재분석하지 않음
- **WHEN** 최신 분석이 최소 재분석 간격 이내인 물건의 감시 필드가 또 변경되면
- **THEN** 그 물건은 재분석 대상으로 선정되지 않고, 간격이 지난 뒤에 선정된다

#### Scenario: 변경 없고 버전도 같은 물건
- **WHEN** 이미 분석되었고 이후 변경이 없으며 프롬프트 버전도 동일한 물건만 있는 상태에서 워커가 실행되면
- **THEN** 그 물건은 재분석되지 않는다

#### Scenario: 신규 분석이 재분석에 밀리지 않음
- **WHEN** 재분석 대상이 신규 한도보다 훨씬 많은 상태에서 미분석 물건도 함께 있으면
- **THEN** 미분석 물건이 먼저 신규 한도만큼 배정되고, 재분석은 자신의 별도 한도 안에서만 처리되어 미분석 물건이 뒤로 밀리지 않는다

#### Scenario: 기존 analyzed 필터 의미 유지
- **WHEN** 클라이언트가 `analyzed=false`로 목록을 조회하면
- **THEN** 재분석 대상 여부와 무관하게 분석 결과가 하나도 없는 물건만 반환된다

### Requirement: Claude 분석 실행
분석 워커는 물건 데이터를 입력으로 Claude 분석을 실행해 결과를 얻어야 한다(SHALL). 분석 결과에는 최소한 요약 평가 텍스트와 감정가 대비 최저매각가격 비율에 대한 코멘트가 포함되어야 한다(SHALL). 개별 물건의 분석 실패는 다른 물건의 분석을 중단시켜서는 안 된다(MUST NOT).

분석 실행 방식은 로컬 headless CLI(`claude -p`)와 Anthropic Messages API 직접 호출을 모두 지원해야 한다(SHALL). 실행 방식은 `ANTHROPIC_API_KEY` 환경변수로 정해져야 한다(SHALL): 값이 설정되어 있으면 Messages API를 사용하고, 설정되어 있지 않으면 로컬 CLI를 사용한다. 컨테이너나 서버 환경에서 CLI 바이너리가 없더라도 유효한 API 키가 설정되어 있으면 분석이 정상 동작해야 한다(SHALL).

분석 입력에는 수집된 확장 필드(면적, 차수별 최저매각가격, 용도 분류, 구조화된 소재지, 사건 비고 등)가 포함되어야 한다(SHALL). 프롬프트는 이 정보로 가능해진 판단 — 면적당 가격, 차수별 저감 추이, 일괄매각 여부가 갖는 의미 — 을 다루어야 한다(SHALL).

값이 없는 필드에 대해 추측해서는 안 된다(MUST NOT). 특히 이 소스로는 **권리관계·임차인·등기 정보를 얻을 수 없으므로**(확인된 사실), 분석 결과는 그 한계를 명시하고 권리분석·현장조사가 필요함을 알려야 한다(SHALL).

분석 입력이나 프롬프트가 바뀌면 프롬프트 버전을 올려야 한다(MUST) — 버전이 그대로면 기존 분석이 낡은 입력으로 생성된 것인지 구별할 수 없다.

#### Scenario: 정상 분석
- **WHEN** 미분석 물건 1건에 대해 분석이 실행되면
- **THEN** Claude 엔진이 물건 데이터를 입력으로 실행되고, 구조화된 분석 결과(요약 평가 포함)가 생성된다

#### Scenario: Direct API 모드 분석
- **WHEN** `ANTHROPIC_API_KEY`가 주어지고 워커가 실행되면
- **THEN** CLI 바이너리 없이도 Anthropic Messages API를 직접 호출하여 분석 결과를 획득한다

#### Scenario: API 키가 있으면 API를 우선 사용
- **WHEN** `ANTHROPIC_API_KEY`가 설정되어 있고 로컬 CLI도 설치된 환경에서 분석이 실행되면
- **THEN** Messages API로 분석하고 로컬 CLI는 호출하지 않는다

#### Scenario: API 키가 없으면 로컬 CLI 사용
- **WHEN** `ANTHROPIC_API_KEY`가 설정되지 않은 환경에서 분석이 실행되면
- **THEN** 로컬 headless CLI로 분석하고 Messages API는 호출하지 않는다

#### Scenario: 개별 분석 실패
- **WHEN** 특정 물건의 분석 실행이 실패하면(CLI 오류, 출력 파싱 실패 등)
- **THEN** 실패가 물건 식별자와 함께 로그에 남고, 나머지 대상 물건의 분석은 계속 진행된다

#### Scenario: 확장 필드를 활용한 분석
- **WHEN** 면적과 차수별 최저가가 있는 물건이 분석되면
- **THEN** 분석 결과가 면적당 가격과 차수별 저감 추이를 다룬다

#### Scenario: 확장 필드가 없는 물건 분석
- **WHEN** 확장 필드가 비어 있는 물건이 분석되면
- **THEN** 분석이 실패하지 않고, 없는 정보에 대해 추측하지 않은 결과가 생성된다

#### Scenario: 프롬프트 버전 상승
- **WHEN** 분석 입력이나 프롬프트가 변경되면
- **THEN** 프롬프트 버전이 올라가고, 저장되는 분석에 새 버전이 기록된다

### Requirement: 분석 결과 수신 API
시스템은 분석 결과를 저장하는 HTTP API(`POST /api/analyses`)를 제공해야 한다(SHALL). 분석 워커는 결과를 이 API를 통해서만 서버에 저장해야 하며(MUST), 결과에는 대상 물건 식별자, 분석 본문, 분석 시각, 사용한 분석 버전(프롬프트 버전) 식별자가 포함되어야 한다(SHALL). 존재하지 않는 물건에 대한 결과는 거부되어야 한다(MUST).

#### Scenario: 결과 저장
- **WHEN** 분석 워커가 유효한 분석 결과를 API로 전송하면
- **THEN** 결과가 해당 물건에 연결되어 저장되고 성공 응답이 반환된다

#### Scenario: 잘못된 물건 식별자
- **WHEN** 존재하지 않는 물건 식별자로 분석 결과가 전송되면
- **THEN** 404(찾을 수 없음) 오류가 반환되고 아무것도 저장되지 않는다

### Requirement: 분석 결과 표시
물건 상세 페이지는 해당 물건의 최신 분석 결과를 표시해야 한다(SHALL). 분석 결과가 아직 없으면 "분석 대기 중"임을 안내해야 한다(SHALL).

같은 물건에 분석이 여러 건 있으면 최신 것을 기본으로 표시하고, 이전 분석도 열람할 수 있어야 한다(SHALL). 이전 분석은 가장 최근 10건까지만 본문을 표시하고, 그보다 오래된 분석은 본문 없이 건수만 알려야 한다(SHALL) — 재분석이 많이 쌓인 물건의 상세 페이지가 한도 없이 커져서는 안 된다(MUST NOT). 각 분석에는 분석 시각과 프롬프트 버전이 함께 표시되어야 한다(SHALL). 재분석은 이전 분석을 삭제해서는 안 된다(MUST NOT).

분석의 최신성 상태를 알 수 있어야 한다(SHALL): 아직 분석되지 않음 / 최신 / 갱신 예정(최신 분석 이후 감시 필드가 실제로 바뀌었거나, 최신 분석의 프롬프트 버전이 현재 버전과 다름). 특히 표시 중인 분석이 현재 값 기준이 아닐 수 있는 경우 그 사실을 알려야 한다(MUST) — 최저가가 떨어진 뒤에도 옛 가격 기준 분석이 최신처럼 보이면 틀린 정보가 된다.

이 판정은 재분석 대상 선정과 같은 변경·프롬프트 버전 규칙을 써야 한다(MUST) — 화면과 워커가 서로 다른 답을 내서는 안 된다. 단, 재분석 최소 간격(쿨다운)은 이 판정에 적용해서는 안 된다(MUST NOT) — 쿨다운은 워커가 이번 회차에 그 물건을 집어들지를 정할 뿐이며, 쿨다운 중에도 표시 중인 분석은 옛 값 기준이므로 갱신 예정으로 보여야 한다.

분석 결과를 보여주는 화면은 **이 데이터 소스로는 권리관계·임차인·등기 정보를 얻을 수 없다는 사실을 상설로 고지해야 한다**(MUST). 분석 본문만 읽은 사용자가 그것을 권리분석까지 포함한 결과로 오해해서는 안 된다(MUST NOT).

#### Scenario: 분석 완료 물건 상세
- **WHEN** 분석 결과가 저장된 물건의 상세 페이지를 열면
- **THEN** 분석 요약과 분석 시각이 물건 정보와 함께 표시된다

#### Scenario: 분석 전 물건 상세
- **WHEN** 아직 분석되지 않은 물건의 상세 페이지를 열면
- **THEN** 물건 정보는 정상 표시되고 분석 영역에는 대기 중 안내가 표시된다

#### Scenario: 재분석된 물건 상세
- **WHEN** 분석이 2건 이상 있는 물건의 상세 페이지를 열면
- **THEN** 최신 분석이 기본으로 표시되고, 이전 분석이 몇 건 있는지와 그 내용을 볼 수 있는 수단이 제공된다

#### Scenario: 이전 분석이 많은 물건 상세
- **WHEN** 분석이 12건 이상 있는 물건의 상세 페이지를 열면
- **THEN** 최신 분석과 이전 분석 10건의 본문이 표시되고, 나머지 이전 분석은 본문 없이 건수만 안내된다

#### Scenario: 이전 분석 보존
- **WHEN** 이미 분석된 물건이 재분석되면
- **THEN** 새 분석이 추가되고 이전 분석은 삭제되지 않는다
#### Scenario: 갱신 예정 표시
- **WHEN** 분석이 저장된 뒤 감시 필드가 변경된 물건의 상세를 열면
- **THEN** 표시된 분석이 갱신 예정 상태임을 알 수 있다

#### Scenario: 쿨다운 중에도 갱신 예정 표시
- **WHEN** 최신 분석이 최소 재분석 간격 이내여서 재분석 대상으로 선정되지 않는 물건의 감시 필드가 변경된 뒤 상세를 열면
- **THEN** 표시된 분석이 최신이 아니라 갱신 예정 상태로 표시된다

#### Scenario: 최신 분석 표시
- **WHEN** 분석 이후 변경이 없고 프롬프트 버전도 같은 물건의 상세를 열면
- **THEN** 그 분석이 최신 상태임을 알 수 있다
#### Scenario: 소스 한계 고지
- **WHEN** 사용자가 분석 결과를 보면
- **THEN** 권리관계·임차인·등기 정보가 이 소스에 없다는 사실이 분석과 함께 표시된다
